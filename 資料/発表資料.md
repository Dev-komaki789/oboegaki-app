## 1. 何を作ったか

**おぼえがき** — 接客業・営業職向けの会話記録アプリ

> **会う直前の30秒で、前回の話を思い出す。**

- **記録アプリではなく判断アプリ。** 既存の人メモアプリは「読んで自分で判断する」で止まる
- **対象は店舗ではなく、そこで働く個人。** 受益者と入力者が同じなので、入力する動機が続く
- 利用シーン：**会う直前の30秒**（思い出す）／**会った後の10秒**（記録する）
- 前提：1日に会うのは4人前後、覚えておく相手は約90人、次に会うのは約2ヶ月後

### 解決する課題（優先順）

| # | 課題 | 機能 | 効き始め |
|---|---|---|---|
| **1** | **「それ前にも答えましたよね」（二度聞き）** | お客さん情報タブ | **初日** |
| **2** | **触れてはいけない話題を振ってしまう** | NG話題の常時警告 | **初日** |
| 3 | 話題は振れるが当たるかが毎回運 | 話題バブル・キーワード | 2ヶ月後 |
| 4 | 前回と同じ話題を続けて振る | 泡の大きさ・最終会話日 | 2ヶ月後 |

**1と2は初日から効く。** データが貯まらないと価値が出ない機能とは分けて考えた。

## 4. 判断したこと ★ここが本体

### ① 盛り上がりを数字にする

**問題**：「この話題は盛り上がるか」を、人の記憶に頼らず判定したい。

**やったこと**：3段構えの計算式。

```
① キーワードごとに指数移動平均（EMA）
   間隔が空くほど新しい値を重く見る（来店ペースの違う業種に同じ式で対応）
② 表示するときに時間で減衰させる
   90日以内 1.00 ／ 181〜365日 0.80 ／ 366日以上 0.65
③ 話題のスコア ＝ 配下キーワードの最高 × 0.7 ＋ 平均 × 0.3
```

**なぜ最高値を7割にしたか**
> **滑ったのは振り方であって、話題ではない。** 最高値で当たりを拾い、平均でノイズに強くする。

**検証**：Python で計算式を書いて7つのケースを実測 → TypeScript に移植 → **全7ケースで値が一致**。

| ケース | 結果 | 判定 |
|---|---|---|
| 当たりの話題を振り続ける | 82前後で維持 | 沈まない ✓ |
| 何を振っても滑る | 43まで低下 | 沈む ✓ |
| 旬が過ぎる | 90 → 88 → 64 → 49 | 落ちる ✓ |
| 当たりを出したきり放置 | 90 → … → 54 | **忘れる** ✓ |

**減衰をどの単位でかけるかで結果が割れた**ので、実測して決めた。

| 方式 | 420日時点のスコア |
|---|---|
| キーワードごとに減衰 | **54.4** ← 採用 |
| 話題に1回だけ減衰 | 80.0 |

後者だと**1年前の当たりが永久に上位に残る**。「古い当たりを忘れる」という要件が壊れる。

### ② セキュリティを「書き忘れられない」形にする

**問題**：顧客情報を扱うので、他人のデータが見えては困る。

**普通のやり方**：ブラウザ → 自前のAPI → DB。APIの中で「このユーザーのぶんだけ」と絞る。
**弱点**：**絞り忘れたら漏れる。** 画面が増えるほど書き忘れの機会が増える。

**やったこと**：**RLS（行レベルセキュリティ）**。PostgreSQL 自身に1行ずつ判定させる。

```sql
create policy "own rows only" on people for all
  using (user_id = auth.uid());
```

**アプリのコードに `where user_id = ...` を1文字も書いていない。**
DB が勝手に条件を足すので、**書き忘れという事故が構造的に起きない。**

**実測**：同じURL・同じコード・同じDBで、ログインしている人だけを変えた。

| | 表示された件数 |
|---|---|
| 本人 | **6件** |
| 別ユーザー | **0件** |

**API を1本も書いていない。** RLS が DB 側で権限を保証しているので、画面から直接 DB を呼べる。

**扱わないものも決めた**：アレルギー・既往歴は対象外。写真も持たない。記録するのは**会話のきっかけになる情報だけ**。

### ③ 「読める」を実測で決める

色や大きさを感覚で決めず、**測って決めた**。

**文字が読めるか**（コントラスト比・4.5以上でAA合格）

| 泡の色 | 白文字 | 黒文字 | 採用 |
|---|---|---|---|
| 薄い緑 | 1.58 | 8.81 | 黒 |
| 中間 | 2.58 | 5.42 | 黒 |
| 濃い緑 | **4.79** | 2.92 | **白** |

> **白文字は最も濃い泡だけに使う。** 中間の緑に白を載せるとコントラスト 2.58 で読めない。

**泡の大きさ**

> 半径を点数に比例させると**面積が二乗で増え、100点が10点の100倍**に見える。
> だから**平方根スケール**を使う。

さらに、指で押せる下限として決めた24pxを**見た目の下限**にしていたら、0点でも直径48pxになり、**泡の大きさが2.7倍幅に圧縮されて差が読めなかった**。

**当たり判定（透明な円）だけ24pxを確保し、見える円は面積を点数に正比例させた。**

| | 最大／最小 |
|---|---|
| 修正前 | 直径 1.75倍（面積 3.1倍） |
| **修正後** | **直径 3.16倍（面積 10.0倍）** |

## 5. 実機で分かったこと（数字）

**PCでは分からないことが、実機で出た。**

### 遅い

| 症状 | 原因 | 対処 | 結果 |
|---|---|---|---|
| **1タップ4秒** | サーバーの実行場所が**アメリカ東部**。1問い合わせごとに太平洋を往復 | **東京リージョンに変更** | **1秒** |
| まだ待たされる | 1画面で**3〜4回**問い合わせを順番に投げていた | **同時に投げる（1回分に）** | |
| 押しても無反応 | 読み込み中に何も出ない | **骨組みを先に出す ＋ 先読み** | **ほぼ一瞬** |

**下限は126ms**（DBを引かない画面の応答）。データ量ではなく**往復の回数**が効いていた。

### 使いにくい

| 症状 | 対処 |
|---|---|
| **スライダーが飛んで違う点数で保存された** | **記録の修正機能**を追加 ＋ 記録画面に **±1ボタン** |
| キーボードが画面の半分を占める | **指で動かしたらキーボードを閉じる** |
| 戻るを何度も押さないと一覧に戻れない | 履歴の積み方を整理（**戻るは pop、タブは replace**） |
| 泡が常時揺れて**酔う** | 動きを**登場と押下のときだけ**に |

**「スライダーが飛ぶ」は、コードでは防げない**（帯をタップすると値が飛ぶのは標準の挙動）。
だから**間違えられる前提で、直せる手段を用意した。**

## 7. 想定質問と答え

**Q. セキュリティは？**
> RLS でユーザーごとにデータを分離しています。他ユーザーのデータには構造的にアクセスできません。
> また、アレルギーなど施術・健康に関わる情報は、そもそも扱いません。記録するのは会話のきっかけになる情報だけです。

**2文で止める。** 暗号化や法律の条文は、聞かれるまで言わない。

**Q. なぜ Supabase？**
> 認証を自作しないためです。5日という期間で、認証の実装に時間を使うのは割に合いません。
> RLS が使えることも大きく、API を1本も書かずに権限を担保できました。

**Q. スコアの計算式に根拠は？**
> Python で7つのケースを実測して決めました。「当たりを出したきり放置すると忘れる」「何を振っても滑る人は沈む」といった、**満たすべき挙動を先に決めて、式を合わせています。**

**Q. 実際に使っているか？**
> （正直に）まだ実運用はしていません。データが貯まって効いてくるのは2ヶ月後の機能なので、そこは今後の検証課題です。**初日から効く「二度聞きを防ぐ」部分は、実機で使える状態になっています。**

**Q. モックアップと違うところがあるが？**
> 実機で確認して直した箇所があります。たとえば一覧のよみがなは、モックアップでは名前の横ですが、**その配置だと名前に使える幅が176pxしかなく「中村 あゆみ」程度でも省略されて**しまいました。名前は識別の要なので、上に移しています。
