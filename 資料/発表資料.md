## 1. つかみ（1分）

> **「それ、前にもお答えしましたよね」**

- 美容師・営業・接客業。**2ヶ月ぶりに会う相手の話を、覚えていられるか**
- 覚えていれば「**そんなことまで覚えててくれたんだ**」が生まれる
- 忘れていれば、その一言で関係が薄くなる

**この差を、記憶力ではなく仕組みで埋める。**

### 何を作ったか

**おぼえがき** — 接客業・営業職向けの会話記録アプリ

> **会う直前の30秒で、前回の話を思い出す。**

- 利用シーン：**会う直前の30秒**（思い出す）／**会った後の10秒**（記録する）
- 前提：1日に会うのは4人前後、覚えておく相手は約90人、次に会うのは約2ヶ月後

### 3-3. 勝ち筋①「生成」ではなく「記録」に振り切る

**根拠**：最有力の ToPic Up は「**サーバに保存しない**」ことをプライバシーの売りにしている。
つまり**構造的に蓄積できない。**

> 既存の雑談アプリは、AIが毎回ゼロから話題を作ります。**過去に何を話したかを覚えていません。**
> このアプリは記録する方向に振り切ります。だから「**前回この話をしました**」と言えます。

**真似されにくい理由**：AI生成型が記録機能を足すことは技術的には可能。
だが「**保存しない**」を売りにしている以上、**方針転換になる。**

---

### 3-4. 勝ち筋② テキストではなく「構造化データ」で持つ

**根拠**：美容室向けシステムは26種類以上あるが、**メモはすべて自由記述のテキスト欄。**

> テキストでは「同じ話を2回していないか」を判定できません。
> **話題を1件ずつレコードとして持つことで、初めて重複警告・点数化・可視化ができます。**

**これが機能の前提になっている。**

```
テキストのメモ  →  読んで自分で判断するしかない
構造化データ    →  重複を警告できる／点数を付けられる／大きさで見せられる
```

**真似されにくい理由**：既存システムのメモ欄を構造化するには、**データモデルの作り直しが必要。**
予約・会計と一体のシステムでは影響範囲が大きい。

---

### 3-5. 勝ち筋③「店舗のもの」ではなく「個人のもの」

**根拠**：美容室向け26種類もSFAも、**会社・店舗が導入するもの。**
面貸し・シェアサロン・フリーランスは使えない。

> 既存の顧客管理は、店舗や会社が導入するものです。**データは組織に残ります。**
> このアプリは個人が持ちます。**転職しても、独立しても、記録は手元に残ります。**

**真似されにくい理由**：業務システム側がこれをやると、**顧客情報の持ち出しを容認することになる。**
店舗経営者向けに売っている以上、構造的にできない。

**入力する動機が続く理由でもある。** 受益者と入力者が同じ人だから。

## 4. なぜこの形にしたか（3分・技術は根拠として）

**技術の話を独立させない。** 上で言った主張の裏づけとして出す。

### 4-1.「構造化データだから点数を付けられる」

勝ち筋②の続き。**盛り上がりを数字にする計算式を作った。**

```
① キーワードごとに指数移動平均（EMA）
   間隔が空くほど新しい値を重く見る（来店ペースの違う業種に同じ式で対応）
② 表示するときに時間で減衰させる（90日以内 1.00 ／ 1年超 0.65）
③ 話題のスコア ＝ 配下キーワードの最高 × 0.7 ＋ 平均 × 0.3
```

**なぜ最高値を7割にしたか**
> **滑ったのは振り方であって、話題ではない。** 最高値で当たりを拾い、平均でノイズに強くする。

**満たすべき挙動を先に決めて、式を合わせた。** Python で7ケースを実測し、TypeScript に移植して**全ケースで値が一致**することを確認。

| ケース | 結果 |
|---|---|
| 当たりの話題を振り続ける | 82前後で維持（**沈まない**） |
| 何を振っても滑る | 43まで低下（**沈む**） |
| 当たりを出したきり放置 | 90 → … → 54（**忘れる**） |

### 4-2.「個人が持つから、構造で分離する」

勝ち筋③の続き。**顧客情報を扱うので、他人のデータが見えては困る。**

普通は「ブラウザ → 自前のAPI → DB」でAPIの中で絞る。**弱点は、絞り忘れたら漏れること。**

**RLS（行レベルセキュリティ）**を使い、**PostgreSQL 自身に1行ずつ判定させた。**

> アプリのコードに `where user_id = ...` を**1文字も書いていません。**
> DB が勝手に条件を足すので、**書き忘れという事故が構造的に起きません。**

**実測**：同じURL・同じコード・同じDBで、ログインしている人だけを変えた。

| | 表示された件数 |
|---|---|
| 本人 | **6件** |
| 別ユーザー | **0件** |

**扱わないものも決めた**：アレルギー・既往歴は対象外。写真も持たない。
記録するのは**会話のきっかけになる情報だけ。**

## 5. まとめ（2分）

### やらなかったことと、その理由

| やらなかった | 理由 |
|---|---|
| AIで話題を生成する | **既存と同じ土俵になる。** 記録型としての差別化が薄れる |
| 「天気」を初期話題に入れる | 検証で**35前後**にしかならず、**バブル10個の枠を1つ無駄にする** |
| 「その他」を初期話題に入れる | **あると全部そこに逃げる** |
| 一覧に総合スコアを出す | **点数を付けるのは話題であって、人ではない** |
| オフライン対応 | 同期の競合解決が必要。5日では無理 |

### 最後の1枚

> 機能で既存を全部超えるつもりはありません。
> **同じ課題に対して、どう設計するかを示したいと考えています。**
>
> 既存はテキストメモ、このアプリは構造化データ。
> **この違いが、重複警告という機能を可能にしています。**

## 6. 想定質問と答え

**Q. ChatGPTでよくないですか？**
> ChatGPTは相手のことを知りません。このアプリの価値は話題を作ることではなく、**その人との過去を思い出せること**です。

**Q. メモアプリでよくないですか？**
> メモアプリは探すのに時間がかかります。会話の直前に必要なのは、**開いた瞬間に「この人にはこれ」が出てくること**です。

**Q. 既存のカルテシステムにもメモ欄がありますが？**
> あります。ただし**自由記述のテキスト欄**です。テキストでは重複判定も点数化もできません。**構造化して持つことが、この機能の前提です。**

**Q. 顧客情報を扱って大丈夫ですか？**
> RLSでユーザーごとにデータを分離しています。他ユーザーのデータには構造的にアクセスできません。
> また、アレルギーなど施術・健康に関わる情報は、そもそも扱いません。記録するのは会話のきっかけになる情報だけです。

**2文で止める。** 暗号化や法律の条文は、聞かれるまで言わない。

**Q. 競合に勝てますか？**
> 機能で既存を全部超えるつもりはありません。**同じ課題に対して、どう設計するかを示したい**と考えています。
> 既存はテキストメモ、本アプリは構造化データ。**この違いが重複警告という機能を可能にしています。**

**Q. 実際に使っているんですか？**
> （正直に）まだ実運用はしていません。データが貯まって効いてくる機能は2ヶ月後の検証課題です。
> **初日から効く「二度聞きを防ぐ」部分は、実機で使える状態になっています。**

**Q. スコアの計算式に根拠は？**
> Python で7つのケースを実測して決めました。「当たりを出したきり放置すると忘れる」「何を振っても滑る人は沈む」といった、**満たすべき挙動を先に決めて、式を合わせています。**
