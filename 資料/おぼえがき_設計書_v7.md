# 1. アプリ概要

## 1.1 コンセプト【v5で拡張】

> **文字だらけのメモは、もう読まない。**
> **会う直前の30秒で、前回の話を思い出す。**

繰り返し会う相手との会話を記録し、次に会う直前に「何を話すか」を判断できるようにする。

### 中核にある価値

**覚えている義理のない、何気ない話を覚えている。**

契約条件も施術の希望も、記録するのが仕事なので覚えていて当然。
一方「息子さんが野球をやっている」は、覚えていなくても誰も困らない。
**だからこそ、覚えていると伝わる。**

> 「そんなことまで覚えててくれたんだ」

この一言が生まれる状態をつくることが、このアプリの目的。

### 記録アプリではなく、判断アプリ

```
既存の人メモアプリ  人を記録する    → 属性が溜まる   → 見返す
おぼえがき          会話を記録する  → 判断材料が溜まる → 使う
```

既存はすべて自由記述なので、会う直前にメモを読んで自分で判断する必要がある。
本アプリは**バブルを見れば判断が終わる**（詳細は12章）。

## 1.2 提供対象【v2で明確化】

**店舗ではなく、そこで働く個人に提供する。**

- 導入を決めるのは本人。使うのも本人。データも本人のもの
- 受益者と入力者が同一人物なので、動機が続く
- 記録する場所・時間を店舗に縛られない（帰宅後でも構わない）
- 転職しても手元に残る

## 1.3 解決する課題（優先順）

| # | 課題 | 対応する機能 |
|---|---|---|
| **1** | **「それ前にも答えましたよね」を防ぐ**（二度聞き） | お客さん情報タブ |
| 2 | 触れてはいけない話題を振ってしまう | NG話題の常時警告 |
| 3 | **話題は振れるが、当たるかどうかが毎回運**（空振り） | 話題バブル・話題詳細のキーワード |
| 4 | 前回と同じ話題を続けて振る | 泡の濃淡・最終会話日 |
| 5 | 会話が広がらない | まだ話していない話題 |

**3について【v5で修正】**
v4までは「何を話せばいいか分からない」と書いていたが、これは不正確だった。
経験のある接客業なら、話題は振れる。当たり障りのない話から入り、反応を見ながら探れる。
**問題はその場を乗り切れてしまうこと。** 当たりを引いても記録されないので、
7年やっても探り方は1年目と変わらない。

**「困っている自覚がない」ことが、このアプリの最大の障壁でもある。**

## 1.4 なぜ必要か（数字の根拠）【v5で調査データを追加】

### 会話がリピートを動かしている（実データ）

**出典：リクルート ホットペッパービューティーアカデミー
「美容室での会話に関する意識調査」2024年5月・男女2,000人**

| 項目 | 数値 |
|---|---|
| 美容室で会話を**したい**人 | **47.2%** |
| 会話を**したくない**人 | **52.9%** |
| 会話が良かったから「また行こう」と思ったことがある | **57.2%**（20代は6割超） |
| 会話が嫌だったから「もう行かない」と思ったことがある | **4割以上** |

**読み取れること**

1. **会話は、続けさせも、辞めさせもする。** 57.2%と4割超という数字がそれを示す
2. **半数以上は会話を望んでいない。** 全員に雑談すればいいという話ではない
   → 調査自身が「その日によっても気持ちは変わるので、**一人ひとりにあわせた細やかな対応が必要**」と結論づけている
3. → **相手ごとに記録する必要がある**。このアプリの存在理由そのもの

**楽しかった／役に立った話題の上位は「髪の悩み」「自宅での髪のケア」**（男女とも）。
食・グルメ、美容・健康も入る。

→ 髪の悩みは**毎回その場で聞けるので記録が要らない**。
　 記録が必要なのは「前に話した引っ越しの件」のような、覚えていないと出てこない話。

### 記録は軽い。でも記憶は無理。

```
1日に会うのは4人前後。記録は数分で終わる
しかし覚えておく相手は約90人。次に会うのは約2ヶ月後
```

**「書けるタイミング」と「思い出せないタイミング」が、完全にずれている。**

### 参考：リピートしない理由ランキング

1位「行きやすい場所にあるから」／2位「担当者の技術や提案があるから」／
3位「スタッフや客層の雰囲気が自分に合っているから」

**立地が1位、技術が2位。** 会話は単独では上位に来ない。
→ **技術力・提案力は大前提**であり、その上に会話が乗る。

### 営業職について【v5で扱いを変更】

v4まではサブペルソナとして法人営業を置いていたが、**プレゼンからは外す。**

理由：**契約が担当者との関係で決まるという裏付けが取れなかった。**
- グリーゼ調査（2021）：約82%が意思決定を終えた状態で営業担当と会っている
- IDEATECH調査：候補選定の決め手は「業界特化情報」が6割超
- HubSpot調査（2019）：訪問を希望する理由は「誠意」と「安心感」だが、成約率との関係は不明

**アプリの機能としては引き続き営業でも使える**（会社名検索など）。
ただし発表では、データの裏付けがある美容師に絞る。

## 2.2 設計上の重要な判断

### 判断1：話題をテキストではなく構造化データで持つ

**既存の美容室向けシステム26種類以上は、すべてメモが自由記述のテキスト欄。**
テキストでは以下ができない。

- 同じ話題を2回振っていないかの判定
- 盛り上がりの点数化
- 大きさによる可視化

**1話題＝1レコードにすることが、すべての機能の前提になっている。**

### 判断2：カテゴリを廃止し、話題に一本化する【v2で変更】

v1では「家族／暮らし／好き・趣味／仕事…」を**カテゴリ**、「野球／旅行／猫」を**話題**として別々に持っていた。
しかし**どちらも「何の話をしたか」であり、性質は同じ**。

```
旧：カテゴリ（家族）＋ 話題（野球）＋ 情報（お子さんが4歳）  ← 3系統
新：話題（家族／スポーツ）→ キーワード（お子さん／大谷翔平）      ← 2層
```

**利点**
- 記録画面からチップ群が1セット消える（入力が軽くなる）
- ユーザーが「これはカテゴリ？話題？」と迷わない
- テーブルが2つ減る（categories / fact_categories）

**代償**
- 話題の粒度を揃える必要がある（後述）

### 判断3：話題は大枠、キーワードが具体【v2で追加】

| 層 | 例 | 性質 |
|---|---|---|
| **話題** | 家族／暮らし／仕事／ペット／スポーツ／旅行／食 | 器。10〜12個程度に収まる |
| **キーワード** | お子さん／引っ越し／ミケ／大谷翔平／沖縄／カレー | その人固有の具体 |

**なぜ話題を大枠にするか**
- バブル10個が安定する。毎回同じ顔ぶれが並ぶので、前回どこが濃かったかを覚えやすい
- 「野球／サッカー／テニス」と細かく分けると、10個の枠を1ジャンルが占有してしまう

**なぜバブルにキーワードを出さないか**
- 1話題が3〜4個に分裂し、10個が30個になる。パッと見て分かる長所が消える
- 「まだ話していない」が表現できない（「大谷翔平、まだ」は意味を成さない）
- 振るのは大枠、中身は会話に入ってから思い出す。この順が実際の会話に合っている

**そのぶんキーワードの重要度が上がる**
「スポーツ、盛り上がり88」だけでは一言目が作れない。
話題詳細でキーワードと話した内容が見えて、はじめて「WBC見ました？」が出てくる。
→ **F-08 話題詳細は、実質コア機能に近い**

### 判断4：1記録＝1話題【v2で追加】

v1のモックアップは、1回の記録で内容を複数行入力できた。
このとき**どの内容がどの話題に紐づくか判定できない**。

```
・大谷翔平がHRを打った    ┐
・カレーを作って美味しかった ┘ → 両方が「スポーツ」になってしまう
```

**採用案：1話題ずつ保存し、続けて次を書く**

```
[保存して、次を書く]   [保存して閉じる]
```

「次を書く」で同じお客さんのまま空のフォームに戻る。

**なぜ「1画面に複数行＋行ごとに話題」ではないのか**

| | 1話題ずつ（採用） | 行ごとに話題 |
|---|---|---|
| 画面の長さ | 短い。片手で完結 | 縦に伸びる |
| 中断時 | 1件目は保存済み | 全部消える |
| 心理的負担 | 短いフォーム×2 | 長いフォーム×1 |
| 所要時間 | やや長い | やや短い |

帰宅後・移動中に片手で使う前提なので、**中断に強く、画面が伸びない方**を採る。
そもそも「変わり映えしない日は内容を書かない」ため、2件書く日はそう多くない。

### 判断5：内容は任意、話題＋盛り上がりは毎回必須【v4で更新】

**前回と同じ話をして、同じように盛り上がった日**は、書くことがない。
無理に書かせると続かない。

一方で、**そこで記録を止めるとスコアが更新されない**。実際は毎回盛り上がっているのに、バブルが古い値のまま止まってしまう。

| 項目 | 頻度 | 所要 |
|---|---|---|
| 話題 | **毎回** | チップ1タップ |
| 盛り上がり | **毎回** | スライダー1秒 |
| キーワード | 任意（推奨） | サジェストから1タップ |
| 話した内容 | **新しい話があった日だけ** | 8秒/件 |

**内容が空でも保存できることが、この設計の要になる。**
同じ話で盛り上がっただけの日は10秒で終わる。

### 判断5-2：内容の欄は1つにする【v4で追加】

v3では2つに分けていた。

```
会話で分かったこと … 阪神ファン（ずっと使える事実）
会話ログ         … 大谷がまたHRを打った（その日限り）
```

モックで確認したところ、**書き分けの判断が入力を重くし、画面も見づらくなった。**

**「話した内容」1欄に統合する。**

| 分けた場合 | 統合した場合 |
|---|---|
| 表示は綺麗に分かれる | 混ざる |
| 毎回「どっち?」を判断する | 書くだけ |
| 記録画面が縦に伸びる | 4項目で収まる |
| 情報タブに凡例・記号が要る | 日付と話題名だけ |

**判断10（ノイズは仕組みで吸収する）と同じ理屈。**
混ざっても日付が付いているので古いものは古いと分かる。困ってから分ければよい。

**結果として facts テーブルが不要になり、records に一本化された（7.1）。**

### 判断6：NGは点数と別に持つ

「反応が薄い（20点）」と「触れてはいけない」は意味が違う。
**0点でも「出さない」にはならない**ため、`is_ng` を別カラムで持つ。

**理由は保存しない**（要配慮個人情報になり得るため＋実装の簡略化）。

### 判断7：NGは専用ページに隠さない

専用ページに分けると**見ずに地雷を踏む。**
タブの外側・上部に1行で常時表示し、タブを切り替えても消えないようにする。

一方、**低得点の話題は専用ページ不要。** TOP10表示にすれば自然と圏外に落ちる。

### 判断8：扱わない情報を明示する

**アレルギー・既往歴など、施術や健康に関わる情報は扱わない。**
それは既存のカルテアプリ・業務システムの領域。

本アプリが記録するのは、**会話のきっかけになる情報だけ。**

### 判断9：話題マスタはユーザー単位

全ユーザー共通にすると、他人が作った不適切な話題名が全員に出るリスクがある。
10日では通報・除外機能まで作れないため、**ユーザー単位**とする。

使い始めの候補が少ない問題は、**初期マスタ**を `user_id IS NULL` で持つことで解決。
v2では話題が大枠になったため、**初期マスタは10〜15語程度**でよい。

### 判断10：ノイズは仕組みで吸収する。ユーザーに判定させない【v3で追加】

記録には必ずノイズが混ざる。

- たまたま相手の機嫌が悪かった日の低得点
- 表記ゆれ（大谷翔平／大谷／オオタニ）
- キーワードを付け忘れた記録
- 盛り上がりを適当に置いた日
- 2ヶ月後に思い出しきれずに書いた曖昧なメモ

**これらに個別対策を入れない。** 対策を足すたびに入力か実装が重くなるため。

**理由**
1. **判定できない。** 機嫌が悪かったのか話題が滑ったのかは、本人にも分からない。分からないものを入力させても入るのは推測でしかない
2. **一時的で済む。** 順位が2ヶ月下がっても、そのとき別の話題を振るだけ。損失は取り返せる
3. **精度が要らない。** 必要なのは10個の中の順位であって、88と73の差ではない

**7.5の計算式そのものが、この方針の実装。**
EMAが1回の値を丸ごと採用せず、時間減衰が古い値を忘れ、最高値が外れ値に引きずられない。
**ノイズ前提で作ってあるから、個別対応が要らない。**

**ただしNG話題は例外。**
「触れてはいけない」はサンプルが増えても薄まらず、1回の失敗が取り返しつかない。
だから点数と切り離して `is_ng` で持ち、常時表示する（判断6・判断7）。

**ノイズとして扱ってよいものと、扱ってはいけないものを分ける。** これが線引きの基準。

### 判断11：点数を付けるのは話題であって、人ではない【v5で追加】

**人単位の総合スコアは持たない。** 技術的には容易だが、倫理的に許容できない。

記録しているのは「この人とはこの話題で盛り上がった」という**会話の事実**であり、
人物の評価ではない（判断8・8.2と同じ方針）。

**実装上の帰結**
- `people` にスコアのカラムを持たない
- 一覧画面に数値を一切表示しない
- 数字が出るのは、詳細を開いて話題タブに入ってから
- **第三者に画面を見られても、数字が話題に付いていることが分かる配置にする**

最後の一項が重要。「田中さん 80点」に見える画面は、見られた時点で終わる。

### 判断12：写真も日記も扱わない【v5で追加】

競合3アプリ（12章）はいずれも写真を中核に置いている。本アプリは写真を持たない。

**理由1：用途が違う**

| | プライベート向け | 本アプリ |
|---|---|---|
| 目的 | 思い出を残す | 次に活かす |
| 手段 | 写真・日記・アルバム | 話題・数値・順位 |
| 使うとき | 見返して楽しむ | 会う直前に判断する |

**機能を削ったのではない。用途が違うから機能が違う。**

**理由2：そもそも撮れない**

競合最大手のメモリオは「AI似顔絵生成」を目玉機能にしている。
写真なしで髪型・メガネ・年齢層を選ぶとアイコンが生成される仕組みで、
**「初対面で写真は撮れない」という前提**に立って作られている。

794件の評価を持つアプリがここを目玉にしているということは、
**顧客や取引先の写真は現実的に撮れない**ということ。ビジネス特化ならなおさら。

本アプリの「見た目の特徴（1行）」は、同じ課題をより軽く解いている。

**理由3：PWAではきれいに保存できない**

| 方法 | 費用 | PWAで可能か |
|---|---|---|
| Supabase Storage | **開発者持ち。ユーザー数に比例して増え続ける** | ○ |
| ユーザーのGoogle Drive | ユーザー持ち | △ OAuth＋Drive APIが必要 |
| ユーザーのiCloud | ユーザー持ち | **× Web APIが存在しない** |
| 端末内（IndexedDB） | なし | △ **機種変更で消える／iOSが削除する可能性** |

競合はいずれも自前サーバーに写真を抱えていない
（メモリオはユーザーのGoogle/Appleアカウントに保存、ヒトメモは機種変更コード、
人記録はCSV/JSON出力）。
**ネイティブアプリならOSの仕組みを使えるが、PWAには相当する経路がない。**

※将来ネイティブ化する場合に、改めて検討する。現時点では入れない。

### 判断13：グループは持たない【v6で廃止】

v5では `people.group_id` を用意し、仕事／プライベートで分ける想定だった。
**v6でこれを廃止する。**

**理由：会社名で絞り込めるため、ビジネス用途では不要**

グループが要る場面を検討したが、どれも成立しなかった。

| 想定用途 | なぜ不要か |
|---|---|
| 会社ごとに分ける | **`company` で検索できる**（判断14） |
| 担当エリア／業界で分ける | 一覧を切り替えたい場面が日常的にない。会う直前に見るのは常に1人分 |
| 既存客／新規開拓で分ける | 同上 |
| 仕事／プライベートで分ける | **ビジネス特化にした以上、プライベートを混ぜる前提を持たない** |
| 前職の顧客と分ける | 転職時に一度整理すれば済む。常設UIを持つ理由にならない |

**削減できるもの**
- 登録画面から1項目
- 詳細画面のプロフィールから1行
- 一覧の絞り込みUI

**※ `people.group_id` のカラムだけは残す。**
後から必要になったときのマイグレーションを避けるため。既定値1を入れておく。

### 判断14：会社名と役職を持つ（BtoB対応）【v6で更新】

`people` に `company`（会社名）と `position`（役職）を**任意項目**として持つ。

> v5では「役職は不要」と判断したが、**v6で復活させる。**
> 詳細画面にプロフィールをまとめて表示する形になり、
> 会社名だけだと情報として中途半端になるため。

**会社名の役割：検索**

```
検索「あすなろ商事」
  → 田中さん  前回：食べ物 88
  → 佐藤さん  前回：仕事 72
```

訪問前に**その会社の全員を一度に確認できる**。
11章に未解決として残っていた「営業職での複数担当者」への回答になる。

**役職の役割：表示のみ**
- 検索対象には含めない（「営業部長」で探す場面がない）
- 詳細画面のプロフィールに出す。相手の立場を思い出すため
- **異動や昇進で変わるので、更新されない前提で扱う**（古くても実害が小さい項目）

**会社名の入力はサジェスト方式**
話題・キーワードと同じ仕組みを使う。

```
[あす        ]
  → あすなろ商事        ← 自分が登録済みの会社名から候補
```

1人目だけ打てば、2人目以降は1タップ。**打ち直さないのでタイポも起きない。**

**一覧には表示しない**
検索対象には含めるが、カードには出さない。
**美容師には不要な項目なので、行を増やさない。**（詳細画面では表示する）

**優先度：標準構成。** カラムは最小構成の時点で用意する。

### 判断15：画面に出る数字の意味を、1つに統一する【v6で追加】

v5の設計では、話題詳細に3種類の数字が並んでいた。

```
食べ物 88        ← 階層集約の結果（計算値）
ラーメン 90      ← EMA＋時間減衰の結果（計算値）
明細 45          ← その日の入力値（生の値）
```

**見た目が同じなので、性質の違いが伝わらない。**
「ラーメン90」を見た人は次も90が出ると期待するが、実際の直近は45かもしれない。

**キーワードの数字を外す。**

```
[ラーメン]  [カフェ]  [和菓子]     ← 濃淡だけで順位を示す
```

**なぜ外してよいか**
キーワードチップの役割は**絞り込みボタン**であって、判断を終える場所ではない。
濃淡で「ラーメンが一番濃い」と分かれば、押す先は決まる。

**代わりに、明細にその日の入力値を出す。**

```
2026/02/03  新しいラーメン屋に行ったらしい     45
2026/01/20  二郎系が好き                     85
2025/12/10  和菓子はあまり食べない            40
```

**理由：EMAで均されると、下降トレンドが見えない。**
「平均は高いが、最近は反応が落ちている」を振る前に知りたい。
そして**初期表示は時系列順**なので、ここに情報がないと判断できない。

**結果、画面に残る数字は2種類だけになる。**

| 場所 | 性質 |
|---|---|
| 話題（88） | その話題の総合評価。1画面に1つだけ |
| 明細（45 / 85 / 40） | **その日の入力値。生の記録** |

### 判断16：導出できるものは持たない。ただし読み取りが重いものは例外【v7で追加】

**visits テーブルを削除する。**

「今日会った」という事実は `records.talked_at` から引ける。

```sql
SELECT DISTINCT person_id FROM records WHERE talked_at = CURRENT_DATE;
```

同じ情報を2箇所に持つと、必ずズレる。テーブルを1つ減らす。

**唯一拾えないのは「会ったが何も記録しなかった日」**だが、
話題と盛り上がりだけなら10秒で保存できる設計なので、
会ったなら何かしら記録が残る。何も記録しないなら「今日の記録」に出す必要もない。

**ただし `people.last_talked_at` は残す。**

これも `records` から導出できる冗長カラムだが、**一覧の並び順に使う**ため。

```sql
-- 持たない場合：300人分のサブクエリが検索のたびに走る
SELECT p.*, (SELECT MAX(talked_at) FROM records WHERE person_id = p.id) AS last
FROM people p WHERE user_id = ?
ORDER BY last DESC NULLS LAST;
```

インクリメンタルサーチで1文字ごとに実行されるため、体感に響く。
**更新は保存時の1回だけなので、ズレる余地も小さい。**

`topics.score` も同じ性質。records から毎回計算できるが、
バブルを開くたびに全レコードを集計するのは重いため、topics 側に持つ。

**基準：導出できるものは持たない。ただし読み取り頻度が高いものは、意図的な非正規化として持つ。**

| カラム | 導出可能か | 持つ理由 |
|---|---|---|
| `people.last_talked_at` | ○ | 一覧の並び順。検索のたびに集計したくない |
| `topics.score` | ○ | バブル表示のたびに全レコードを集計したくない |
| ~~`visits`~~ | ○ | **読み取り頻度が低い。削除**（F-10でしか使わない） |

名前・よみがな・見た目・**会社名**を OR 条件でまとめて引く。窓を分けない。

```

「あすなろ」→ 会社名にヒット。その会社の担当者が全員出る

```

**窓を分けない理由**
- 打つ側が「どちらに入れるか」を毎回判断しなくて済む（判断10）
- 画面に入力欄をもう1つ置く余白がない
- 美容師には会社名の欄が不要なので、常に空の窓が見えることになる

**会社名と人名が混ざる件**
「佐藤」で佐藤製薬と佐藤さんが混ざるケースは実在する。
ただし**結果は数件に収まる**ため、一覧を見れば区別できる。
→ 判断10（ノイズは仕組みで吸収する）の対象として許容する。

**1件あたりのサイズは詰めない**
280人を上からスクロールする想定ではなく、**検索で数件に絞ってから選ぶ**画面。
余白があった方が、同姓同名の見分けもタップも確実になる。

### 見た目の特徴（appearance）の扱い【v7で追加】

**入力：1つの欄に「、」区切りで書く。個数の制限はしない。**

```
ショートボブ、眼鏡、いつも黒い服
```

入力時に個数を弾かない理由は、**何を捨てるかの判断を発生させたくない**ため（判断10）。

**保存：`text` のまま。分割して別テーブルにはしない。**

| | text のまま | 別テーブル |
|---|---|---|
| 検索 | `ILIKE` 一発 | JOIN が要る |
| 入力 | 1欄 | 変わらない |
| 集計 | できない | できる |

「眼鏡の人が何人いるか」を集計する予定はない。**表示のために分けるだけ**なら text で足りる。

**表示：画面によって出し分ける。**

| 画面 | 表示 |
|---|---|
| **一覧（S-02）** | 区切って個別のバッジ。**最大2行。溢れた分は「+N」で省略** |
| **詳細（S-04）** | すべて表示 |

**一覧のバッジ表示ルール**

```
・年代・性別のバッジも同じ行に含めて数える
・1行に収まらないバッジは2行目に折り返す
・2行に収まらない分だけ「+N」で省略する
・バッジ単体を「…」で切らない
  → 丸ごと表示するか、+N に含めるかの二択
```

**なぜ2行までか**

1行だと情報量が少なすぎる。一方、無制限だとカードの高さがばらつき、
スクロール時に視線が安定しない。**高さが1行と2行の2種類に収まる**のがちょうどいい。

**なぜバッジ単体を途中で切らないか**

「インナーカラー…」では何の特徴か分からず、同姓同名の識別に使えない。
省略するなら、そのバッジごと「+N」に含める。

**分割は複数の区切り文字を許容する。**

```js
appearance.split(/[、,，・]/).map(s => s.trim()).filter(Boolean)
```

全角読点・半角カンマ・全角カンマ・中黒のどれで入力されても分割できる。

**検索は区切り文字を意識しない。**

```sql
appearance ILIKE '%眼鏡%'
```

「ショートボブ、眼鏡」に対して「眼鏡」で部分一致する。**分割しない方が検索は単純。**


話題ごとに白カードでグルーピングする。

### S-06 詳細／タブ②「話題バブル」【v6で更新】
```
大きいほど盛り上がった   薄いグレー＝前回話した
─────────────────────────────
          [ 旅行 ]
     [ 車 ]      [ 食べ物 ]         ← 実線10個のみ
  [ 暮らし ] [ 仕事 ]  [ 天気 ]
     [ 地元 ] [ 健康 ]
     [ ペット ]    [ 家族 ]
   ※円の中は 話題名 ＋ 最終会話日
─────────────────────────────
まだ話していない： お酒  音楽  スポーツ   ＞
─────────────────────────────
盛り上がった順  全10件
 食べ物 ━━━━━━━━ 88
 ペット ━━━━━━━  83
 旅行   ━━━━━━   77
```

**v1からの変更点**

| | v1 | v2 |
|---|---|---|
| 点線バブル | バブル群に混在 | **廃止。下に1行のチップで表示** |
| バブル数 | 可変 | **実線10個で固定** |
| 11位以下 | — | **押し出される。下のリストで確認できる** |

**点線を分けた理由**
点線バブルには大きさの意味がない（盛り上がりが未計測なため）のに、大きさを持っていた。
「甲子園（点線）が猫（実線）より大きく見える」状態が起き、**大小＝盛り上がりのルールが崩れていた。**
実線だけにすることで、バブルの読み方が一意になる。

**押し出しの仕様**
- 並び順は盛り上がり順。11位以下はバブルから消えるが、**データは消えない**
- 下のリストをスクロールすれば全件見える
- ※7.5の時間減衰により、放置された話題は自然に沈む

**「最有力」カードは置かない【v4】**
v3では最上位話題の直近ログを先出しする案を検討したが、モックで確認したところ
バブルと競合して目が散るため廃止。**バブルを1つタップすれば足りる。**

### S-07 話題詳細【v6で更新】
```
話題に戻る
─────────────────────────────
食べ物                          盛り上がり
前回 2026/02/03                      88

[ラーメン]  [カフェ]  [和菓子]     ← 数字は出さない（判断15）
キーワードをタップすると絞り込めます
─────────────────────────────
話した内容
2026/02/03  新しいラーメン屋に行ったらしい     45
2026/01/20  二郎系が好き                     85
2026/01/20  近所のカフェが閉店して残念        72
2025/12/10  和菓子はあまり食べない            40
                          もっと見る
```

**キーワードのチップ【v6で変更】**
- **数字は表示しない。** 濃淡だけで順位を示す（判断15）
- 並びは盛り上がった順（登場回数ではない）
- タップすると、そのキーワードの内容だけに絞り込まれる

**なぜ数字を外したか**
キーワードのスコアはEMAで均された値で、明細の生の値と性質が違う。
同じ見た目で並ぶと「ラーメン90だから次も90」と誤解される。
**チップは絞り込みボタンであり、判断を終える場所ではない。** 濃淡で順位が分かれば足りる。

**明細の右端に、その日の入力値を表示する【v6で追加】**

| 場所 | 何の数字か |
|---|---|
| 話題（88） | 配下キーワードから階層集約で算出（7.5③） |
| **明細（45 / 85 / 72 / 40）** | **その日に入力した生の値。`records.score` をそのまま表示** |

**なぜ明細に出すか**

キーワードのスコアはEMAで均されるため、**下降トレンドが見えない。**

```
2026/02/03  45   ← 直近は落ちている
2025/11/15  88
2025/08/20  92
```

「平均は高いが、最近は反応が落ちている」を振る前に知りたい。
そして**初期表示は時系列順**なので、ここに情報がないと判断できない。

**表示は控えめにする。** 右端に小さくグレーで。数字が主役にならないように。

- **セクション分割はしない**（判断5-2により内容が1種類になったため）
- 直近5件を表示し、下に「もっと見る」

**この画面が一言目をつくる。**
「食べ物 88」だけでは話が始まらない。
「新しいラーメン屋に行った」があってはじめて「どうでした?」が出る。

### S-08 記録する【v6で更新】
```
閉じる    記録する              田中 みか
─────────────────────────────
話題                            ← 必須
[話題を入力／下から選ぶ    ]
 家族  スポーツ  旅行  ペット  食  ＋新しい話題

キーワード  任意                 ← サジェスト付き
[おお              ]
  → 大谷翔平 / 大久保さん        ← 候補
 大谷翔平  阪神  甲子園

盛り上がり                  90   ← 必須
  いまいち  普通  良い  すごく
  ●━━━━━━━━━━━━━━━○━

話した内容  任意
同じ話で盛り上がっただけなら、書かなくて構いません
[例：大谷がまたHRを打った  ] [＋]
  ＋ もう1つ書く

□ この話題は避けたほうがいい
─────────────────────────────
   [保存して、次を書く]  [保存して閉じる]
```

**入力欄は4つだけ。**

| 項目 | 必須 | 所要 |
|---|---|---|
| 話題 | ● | 3秒 |
| キーワード | | 2秒 |
| 盛り上がり | ● | 4秒 |
| 話した内容 | | 8秒/件 |

**必須が上3つに集まっているため、内容を書かない日は約10秒で保存できる。**

**v3から削ったもの**
- 「会話で分かったこと」と「会話ログ」の2欄 → **「話した内容」1欄に統合**（判断5-2）
- 「次に聞きたいこと」 → **廃止**（出口の設計が固まらず、入力だけ増えていた）

**「＋ もう1つ書く」は残す**
同じ話題の中で内容が2件になるケースがあるため。
**話題が同じなら混ざらないので、判断4の問題は起きない。**

# 4. 入力の仕組み

## 4.1 話題選択（チップ方式）

### 表示の2段階

| | 対象 |
|---|---|
| 初期表示のチップ | **そのお客さんに紐づく話題**（＝これまで話したことがあるもの） |
| 入力して絞り込む対象 | **そのユーザーの話題マスタ全件**（他のお客さんで使ったものも含む） |

**入力欄は検索窓であり、選択の実体はチップ側にある。**

### 並び順
**よく使う順。** 固定順だと毎回同じ位置を探すことになる。

### 入力欄は「チップ製造機」

```
[やまのぼり        ] [＋]  ← ＋ボタン（またはEnter）
        ↓
やまのぼり ✓ NEW   野球 ✓      ← チップ化され選択状態に
[                  ]           ← 入力欄は空に戻る
```

- **「新規登録ボタン」は置かない**（二度手間になる）
- 既存にあれば → そのチップが選択状態になる（新規作成しない）
- 既存になければ → 新しいチップが作られて選択状態になる
- **判定はシステム側が行い、ユーザーは意識しない**

**※v2では話題は単一選択**（1記録＝1話題のため）。
チップ製造機の仕組みはキーワード側で引き続き活きる。

### 初期話題マスタ（10個）【v7で並び順を確定】

`topic_masters` に `user_id IS NULL` で投入する。**アプリ全体で1セットだけ。**

| sort_order | 話題 | キーワード例 | 上位に置く理由 |
|---|---|---|---|
| 1 | 家族 | お子さん／ご両親／兄弟 | 誰とでも話せて、次回への続きがある |
| 2 | 食べ物 | ラーメン／カフェ／お酒 | 調査の話題ランキング上位。2ヶ月後まで持つ |
| 3 | 暮らし | 引っ越し／通勤／家 | 変化があると相手から話題が出る |
| 4 | 仕事 | 転職／異動／繁忙期 | 相手から出やすい |
| 5 | 旅行・おでかけ | 沖縄／温泉／ディズニー | 季節性がある |
| 6 | 健康・美容 | 肌荒れ／睡眠／ダイエット | 調査では最上位だが、専門相談寄り（後述） |
| 7 | 趣味 | カメラ／読書／ゲーム | 個人差が大きい |
| 8 | エンタメ | ドラマ／音楽／推し | 同上 |
| 9 | ペット | 猫／犬 | 当たれば強いが、母数が少ない |
| 10 | スポーツ | 野球／サッカー／ジム | 同上 |

**並び順の基準：上ほど誰にでも当てはまり、下ほど当たれば強いが人を選ぶ。**

**「健康・美容」を6番に置いた理由**
調査では「髪の悩み」「自宅での髪のケア」が話題ランキング1位だった（1.4）。
ただしこれは**毎回その場で聞くもの**で、記録して思い出す性質ではない。
チップの上位に置く必要は薄いと判断した。

**選定の考え方**

- **粒度を揃えた。** すべて「器」で、その下に具体が入る（判断3）
  「野球」ではなく「スポーツ」、「猫」ではなく「ペット」
- **「天気」を入れない。** 誰とでも話せるが盛り上がらないため必ず下位に沈み、
  **バブル10個の枠を1つ無駄にする**（7.5の検証で35前後と確認済み）。必要なら自分で追加する
- **「その他」を入れない。** あると全部そこに逃げ、分類が機能しなくなる

**使いながら自分の話題を追加すれば、初期の10個は自然に押し出されていく。**

### 記録画面のチップの並び順【v7で確定】

**2段階で決める。**

```
① そのお客さんとの実績がある → 話した回数の多い順
② なければ（新規のお客さん） → 初期マスタの sort_order 順
```

```sql
-- ① 実績順
SELECT tm.id, tm.name, COUNT(r.id) AS cnt
FROM topics t
JOIN topic_masters tm ON tm.id = t.topic_master_id
LEFT JOIN records r   ON r.topic_id = t.id
WHERE t.person_id = :pid
GROUP BY tm.id, tm.name
ORDER BY cnt DESC LIMIT 5;

-- ② 0件だったときのフォールバック
SELECT id, name FROM topic_masters
WHERE user_id = :uid OR user_id IS NULL
ORDER BY sort_order LIMIT 5;
```

**`sort_order` が効くのはここだけ。** 初日と、新規のお客さんを登録した直後だけ使われる。
2回目以降は必ず実績順に置き換わる。

**検討したが採用しなかった案**
「そのお客さんに実績がなければ、自分の全顧客での使用回数順」という3段階案もあった。
ただし新規顧客を登録した直後にしか効かず、クエリが1本増えるため見送る。後から足せる。

## 4.2 キーワード入力（サジェスト方式）

v1の「カテゴリ選択」を置き換えるもの。

```
[おお              ]
  ↓ 候補が出る
  大谷翔平
  大久保さん
```

- **候補はユーザーの全顧客で使われたキーワードから引く**（そのお客さん限定にしない）
  同じ担当者が扱う語彙は自然と偏るため、横断した方が入力が速い。他人には漏れない
- **並び順は使用回数の多い順**
- 初回だけ手入力、2回目以降は実質1タップ

**既知の弱点：表記ゆれ**
「大谷翔平／大谷／オオタニ」が別キーワードとして登録され得る。
同一顧客内ではサジェストで一貫するが、顧客をまたぐと分裂する。
→ 現時点で横断集計の機能はないため実害なし。将来「野球好きの顧客一覧」を作る際に対応する。

# 5. スマホ（iPhone）向けの配慮

| # | 項目 | 内容 |
|---|---|---|
| M-01 | **IME対応** | Enterは変換確定と競合するため、**「＋」ボタンを主役にする** |
| M-02 | タップ領域 | **44px以上**を確保（Appleガイドライン） |
| M-03 | ボタン配置 | 主要ボタンは**下部固定**（片手では上部に親指が届かない） |
| M-04 | **キーボード対策** | 入力中は**保存ボタンをキーボードの上に浮かせる** |
| M-05 | 検索窓 | **自動フォーカスしない**（一覧が隠れるため） |
| M-06 | スライダー | つまみの当たり判定44px以上／帯を16〜20px／**ドラッグ中は値を拡大表示** |
| M-07 | 補助目盛り | 背景に薄く「いまいち／普通／良い／すごく」。**目盛りで止まるわけではない** |
| M-08 | 泡の最小半径 | 24px以下にしない。リスト併設で補完 |
| M-09 | 本文サイズ | **16px以上**（16px未満の入力欄はiOSで自動ズームが起きる） |
| M-10 | **片手・寝転がり操作**【v2】 | 帰宅後にソファ・ベッドで開く前提。両手で正確にタップする想定にしない |
| M-11 | **日付またぎ**【v2】 | 帰宅が深夜1時の場合、日付上は翌日になる。**午前4時までは前日扱い**にする |
| M-12 | **キーボードで一覧が隠れる**【v5】 | iPhoneのキーボードは画面の約4割。**リストを下に引いたらキーボードを閉じる**挙動を入れる。検索で数件に絞る前提なので、これで足りる |

**M-01とM-04は実機で最もストレスになるため、優先度が高い。**

### 盛り上がりスライダーを1点刻みのままにする理由

5段階にすると「これはめっちゃ刺さったけど、こっちよりは下かな？」という**微妙な上下関係が表現できない。**
同点が量産され、泡の大きさに差が出なくなり、「どっちが鉄板か」が分からなくなる。

**バブル10個に対して5段階では、同じ大きさの泡が3つ並ぶ場面が普通に起きる。**
そのとき「どれから振るか」が決まらない。

**そもそも「68を狙って出す」必要はない。** ざっくり動かした結果が68だっただけなので、指の精度は問題にならない。
**入力コストは4秒/件（1日5人で20秒、全体の1割弱）。** 削っても効果は小さい。

# 6. 使用方法（利用シナリオ）

## 6.1 導入時

1. アカウントを作る
2. **明日の予約が入っているお客さんを5人だけ登録する**（名前だけでよい）
3. 登録時に「この方と最近どんな話をしましたか」を1つだけ入力する
   → **初日から情報がある状態を作る**

**ポイント**：美容師の顧客は年4〜5回しか来ないため、1人だけ登録すると効果を実感するまで2ヶ月かかる。**複数人まとめて登録することで、翌日には効果を体験できる。**

## 6.2 日常の使い方

### ① 会う直前（30秒）
```
一覧を開く → 名前で検索 → 詳細を開く
  ↓
⚠ 避ける話題を確認
  ↓
お客さん情報に目を通す
  ↓
（話題に迷ったら）話題タブ → バブルをタップ → キーワードと話した内容で一言目を作る
```

### ② 会話中
特に操作しない。**アプリを見ながら話すことはない。**

### ③ 記録するとき【v2で変更】

| 職種 | タイミング | 理由 |
|---|---|---|
| 美容師 | **その日のうち。閉店後でも帰宅後でもよい** | 個人向けアプリなので場所を選ばない |
| 営業職 | **訪問直後〜移動中** | 記憶が最も新しい |

**重要なのは時間ではなく状態。「思い出せるうちに書く」。**
場所は店でも電車でも風呂上がりでもよい。だから名前が「おぼえがき」。

```
記録画面を開く
  ↓
話題をチップから選ぶ                 ← 必須
  ↓
キーワードを選ぶ／入力する            ← 任意
  ↓
盛り上がりをスライダーで動かす         ← 必須
  ↓
新しい話があれば「話した内容」を書く    ← 任意
  ↓
[保存して次を書く] or [保存して閉じる]
```

## 6.3 所要時間の試算【v2で追加】

**1人1話題あたり**

| 項目 | 時間 |
|---|---|
| 一覧から開く | 2秒 |
| 話題を選ぶ | 3秒 |
| キーワードを選ぶ | 2秒 |
| 盛り上がり（判断3秒＋操作1秒） | 4秒 |
| 話した内容（1件） | 11秒 |
| 保存 | 1秒 |
| **合計** | **約23秒**（内容2件なら34秒） |

※内容を書かない日は**約12秒**

**1日分**

| | 人数 | 所要 |
|---|---|---|
| 美容師（平均） | 5人 | **2〜4分** |
| 美容師（繁忙） | 7人 | **3〜5分** |
| 営業 | 4社 | **2〜3分** |

**現実には以下で伸びる**
- 新規客の初回：登録が加わり1人90〜120秒
- 4人目、5人目は記憶が薄く、思い出す時間が伸びる
- 中断が入る

**実質5人で5分前後。** 資料の「数分で終わる」は誇張ではない。

## 6.4 使い続けると起きること

| 期間 | 状態 |
|---|---|
| 1日目 | 5人登録。情報が5〜10件 |
| 1週間 | 25人前後。バブルに差が出始める |
| 2ヶ月 | 初回登録の人と再会。**「使えた」を実感する** |
| 半年 | 150人前後。検索なしでは探せない量になる |
| 1年 | 250〜300人。**転職しても手元に残る資産になる** |

**既知の課題：溜まるまで価値が出ない。**
最初の1〜2ヶ月をどう乗り切ってもらうかは未設計（6.1の導入手順が部分的な答え）。

```
│ keyword_id (FK) → keywords  nullable ├─────┘
│ score      0〜100  必須              │
│ content    nullable ← 空でも保存可   │
│ talked_at                            │
└──────────────────────────────────────┘
```

**関係の要点**

| | 説明 |
|---|---|
| users → people | 1人の利用者が複数の顧客を持つ |
| people → topics | **人×話題で1レコード。** 田中さんの「食べ物」と佐藤さんの「食べ物」は別行 |
| topics → records | 1つの話題に複数の記録がぶら下がる |
| records → keywords | nullable。キーワードを付けない記録もある |
| topic_masters | **話題の名前だけを持つマスタ。** スコアは topics 側 |

**topics と topic_masters を分ける理由**
「食べ物」という名前は全顧客で共通だが、スコアは顧客ごとに違う。
名前をマスタに寄せることで、名前変更が1箇所で済む。

### 外部キーと ON DELETE の方針【v7で追加】

PostgreSQL の既定は `NO ACTION` で、**子レコードがあると親を削除できない。**
削除機能を作る以上、すべての外部キーに指定が要る。

| 子テーブル | カラム | 参照先 | ON DELETE | 理由 |
|---|---|---|---|---|
| people | user_id | users | **CASCADE** | アカウント削除で全データを落とす |
| topic_masters | user_id | users | **CASCADE** | 同上 |
| keywords | user_id | users | **CASCADE** | 同上 |
| topics | person_id | people | **CASCADE** | お客さんを消せば、その人の話題も消える |
| topics | topic_master_id | topic_masters | **RESTRICT** | 使用中の話題名は消させない |
| records | person_id | people | **CASCADE** | お客さんを消せば記録も消える |
| records | topic_id | topics | **CASCADE** | 話題を消せば、その話題の記録も消える |
| records | keyword_id | keywords | **SET NULL** | **記録は残す**（後述） |

**keyword_id だけ SET NULL にする理由**

CASCADE にすると、**キーワードを消しただけで会話の記録が消える。**

```
「ラーメン」を削除
  → CASCADE なら「新しいラーメン屋に行った」という内容まで失われる
  → SET NULL なら内容は残り、キーワードの紐づけだけ外れる
```

キーワードは分類のための語であって、**記録の本体ではない**。消して困るのは分類だけ。

**topic_master_id を RESTRICT にする理由**

話題名を消したときに、それを使っている topics まで消えると、
**そこにぶら下がる records も CASCADE で連鎖して消える。**
「食べ物」という名前を消しただけで、食べ物の会話が全部消えるのは事故になる。

使用中なら削除を拒否し、先に topics を整理させる。

**DDLの例**

```sql
CREATE TABLE records (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  person_id   uuid NOT NULL REFERENCES people(id)   ON DELETE CASCADE,
  topic_id    uuid NOT NULL REFERENCES topics(id)   ON DELETE CASCADE,
  keyword_id  uuid          REFERENCES keywords(id) ON DELETE SET NULL,
  score       smallint NOT NULL CHECK (score BETWEEN 0 AND 100),
  content     text,
  talked_at   date NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);
```

**削除が必要になる場面**

| 場面 | 消すもの | 連鎖 |
|---|---|---|
| アカウント削除（App Store審査要件） | `users` 1行 | 全データが CASCADE で落ちる |
| サンプル顧客の削除（11章の対策2） | `people` 1行 | topics / records が落ちる |
| お客さんの削除 | `people` 1行 | 同上 |

**アカウント削除は `auth.users` を消せば `public.users` も CASCADE で落ちる。**
アプリ側で順に DELETE する必要はない。

### 削除したテーブルの履歴

| テーブル | 経緯 |
|---|---|
| ~~categories / fact_categories~~ | v2で話題に統合（判断2） |

## 7.3 情報の3階層

```
people（お客さん）
  └ topics（話題）      … 家族／食べ物／旅行  ← バブル
       └ records（記録） … 内容・スコア・日付
            └ keyword_id … ラーメン           ← 話題詳細で絞り込み
```

| 層 | 例 | スコアの性質 | 表示場所 |
|---|---|---|---|
| **話題**（topics） | 食べ物 | **計算値**（階層集約） | バブル／盛り上がった順リスト |
| **キーワード**（keywords） | ラーメン | **計算値**（EMA＋減衰）。**画面には出さない** | 話題詳細のチップ（濃淡のみ） |
| **記録**（records） | 新しいラーメン屋に行った | **生の入力値** | 情報タブ／話題詳細の明細 |

**画面に出る数字は「話題」と「記録」の2種類だけ**（判断15）。
キーワードのスコアは内部計算にのみ使い、表示は濃淡で行う。

## 7.4 1回の保存で起きること

```
[保存] を押すと
  ↓
1. 新規の話題名・キーワード名があれば、先にマスタへ INSERT
     topic_masters / keywords
2. topics に該当行がなければ INSERT（person_id × topic_master_id）
3. records に 1件 INSERT
     person_id, topic_id, keyword_id, score, content, talked_at
     ※内容を2件書いた場合は2レコード（score は同じ値）
4. topics.score を再計算（7.5の計算式）
5. topics.last_talked_at を更新
6. people.last_talked_at を更新
7. 「この話題は避けたほうがいい」がチェックされていれば topics.is_ng = true
```

**「保存して次を書く」を押した場合**、同じ person_id のまま S-08 を再表示する。

## 7.5 盛り上がりスコアの計算【v3で確定】

### 確定仕様

```
■ キーワードスコア（指数移動平均）
   新score = 旧score × (1 - c) + 今回 × c
   初回は今回の値をそのまま採用

   c（新しい値の重み）は前回からの経過日数で決める
     7日以内   → 0.20
     30日以内  → 0.35
     31日以上  → 0.50

■ 表示値（時間減衰）
   表示値 = キーワードスコア × 減衰率

   減衰率は最終会話日からの経過日数で決める
     90日以内  → 1.00
     180日以内 → 0.90
     365日以内 → 0.80
     366日以上 → 0.65

■ 話題スコア（階層集約）
   話題score = 配下キーワードの表示値の最高 × 0.7
             + 配下キーワードの表示値の平均 × 0.3
```

### なぜこの3段構えなのか

| 段 | 解決している問題 |
|---|---|
| EMA・係数可変 | 単純平均は回数が増えると動かなくなる。最新値のみは1回のブレで乱高下する。**間隔が空くほど新しい値を重く見る**ことで、来店ペースの違う業種に同じ式で対応できる |
| 時間減衰 | 最高値は「忘れない」。1年前の当たりが永久に話題を押し上げるのを防ぐ |
| 最高0.7＋平均0.3 | **キーワードごとの当たり外れを、話題の評価に持ち込まない**（後述） |

### 最高値を主に使う理由

```
スポーツ
  ├ 大谷翔平  90  ← 当たり
  └ イチロー  40  ← 滑った
```

単純平均だと65になり、「スポーツは微妙な話題」と判定されてしまう。
しかし**滑ったのは振り方であって、話題そのものではない。** 大谷を振れば90が出る。

一方、純粋な最高値だけだと「10個中9個滑っても90のまま」になる。
そこで平均を3割だけ混ぜ、周辺の反応も薄く反映させる。

| ケース | 最高 | 平均 | 話題score |
|---|---|---|---|
| 大谷90・イチロー40 | 90 | 65 | **83** |
| 大谷90のみ | 90 | 90 | **90** |
| 全部50 | 50 | 50 | **50** |

**この2段構え（配下は最大値、上位で平均を混ぜる）は、グループ推薦の分野で階層集約と呼ばれる標準的な手法。**
最大値は「当たりを見つける」のに強く、平均は「ノイズに強い」。両方の利点を取る。

### 検証結果

`score_check.py` で以下を確認済み。

| ケース | 挙動 | 判定 |
|---|---|---|
| 大谷90・イチロー40を繰り返す | 82前後で維持 | 沈まない ✓ |
| 何を振っても40前後 | 43まで低下 | 沈む ✓ |
| 旬が過ぎる（90→85→40→35） | 90 → 88 → 64 → 49 | 落ちる ✓ |
| 当たりを出したきり放置 | 90 → 82 → 74 → 65 → 54 | 忘れる ✓ |
| 常連・週1来店 | 80前後で安定 | 暴れない ✓ |
| キーワードが5個に増える | 76.5 | 平準化しない ✓ |

**バブル順位の2年推移（1顧客・シミュレーション）**

```
 6ヶ月  スポーツ89 / ペット83 / 旅行77 / 食69 / 家族63
12ヶ月  スポーツ89 / ペット83 / 旅行77 / 食69 / 家族63
18ヶ月  スポーツ89 / ペット83 / 旅行74 / 食65 / 家族63
24ヶ月  スポーツ88 / ペット83 / 旅行66 / 家族63 / 食58
```

- **上位が安定する** → 2ヶ月ごとに開いても顔ぶれが変わらず、前回どこが濃かったか覚えていられる
- **下位は入れ替わる** → 放置された話題（旅行77→66）が沈み、別の話題が入る
- **天気は毎回話しても35前後**。一度も上位に来ない

### 採用しなかった案

| 案 | 却下理由 |
|---|---|
| 単純平均 | キーワードの当たり外れが話題の評価を潰す（スポーツが65になる） |
| 最新値のみ | 1回のブレで乱高下する |
| 最小値（Least Misery） | 誰も好きでも嫌いでもない平凡な話題ばかりが残る |
| **登場回数** | **汎用話題（天気・仕事）が全顧客で最大になり、全員のバブルが同じ顔になる。** また「振る→回数増→目立つ→また振る」の自己強化ループが起き、同じ話を繰り返す問題を悪化させる |

### 変更可能性の担保

`records` に**生スコアと日付を必ず保存する。**
上記3段はすべてそこからの再計算で求まるため、**実データを見てから係数も方式も変更できる。**

**取り返しがつかないのは「毎回スコアと日付を残すこと」だけ。**

## 7.6 主要クエリ【v6で更新】

### 一覧・検索（S-02）
```sql
SELECT * FROM people
WHERE user_id = :uid
  AND (:q = '' OR
       name       ILIKE '%' || :q || '%'
    OR name_kana  ILIKE '%' || :q || '%'
    OR appearance ILIKE '%' || :q || '%'
    OR company    ILIKE '%' || :q || '%')   -- 会社名で複数担当者をまとめて引ける
ORDER BY last_talked_at DESC NULLS LAST;
```
**窓は1つ。4項目をOR条件で横断する**（判断14）。役職は含めない。
グループでの絞り込みは行わない（判断13で廃止）。

### 会社名のサジェスト（S-03）
```sql
SELECT DISTINCT company
FROM people
WHERE user_id = :uid AND company ILIKE :q || '%'
ORDER BY company LIMIT 5;
```

### 情報タブ・時系列（S-04）
```sql
SELECT r.content, r.talked_at, tm.name AS topic_name,
       (r.talked_at >= :last_visit) AS is_new   -- 【更新】ピルの判定
FROM records r
JOIN topics t         ON t.id  = r.topic_id
JOIN topic_masters tm ON tm.id = t.topic_master_id
WHERE r.person_id = :pid AND r.content IS NOT NULL
ORDER BY r.talked_at DESC;
```
**`content IS NOT NULL` で、スコアだけ記録した日を除外する。**

### 情報タブ・話題別（S-05）
上記に `ORDER BY tm.name, r.talked_at DESC` を使い、アプリ側でグルーピング。

### 話題バブル（S-06／実線10個）
```sql
SELECT t.id, t.score, t.last_talked_at, tm.name
FROM topics t
JOIN topic_masters tm ON tm.id = t.topic_master_id
WHERE t.person_id = :pid AND t.is_ng = false
ORDER BY t.score DESC
LIMIT 10;
```
**NGを除外してスコア順に取るだけ。** 11位以下は自動的に圏外へ落ちる。
「盛り上がった順」リストは `LIMIT` を外して全件取得。

### 話題詳細のキーワード（S-07／濃淡の順）
```sql
SELECT k.id, k.name,
       AVG(r.score)      AS avg_score,   -- 濃淡の決定に使う。画面には出さない
       MAX(r.talked_at)  AS last_at
FROM records r
JOIN keywords k ON k.id = r.keyword_id
WHERE r.person_id = :pid AND r.topic_id = :tid
GROUP BY k.id, k.name
ORDER BY avg_score DESC;
```
**数字は画面に出さない**（判断15）。取得した値は濃淡の決定にのみ使う。

### 話題詳細の明細（S-07）
```sql
SELECT r.content, r.talked_at, r.score      -- score をそのまま表示（判断15）
FROM records r
WHERE r.person_id = :pid AND r.topic_id = :tid
  AND r.content IS NOT NULL
  AND (:keyword_id IS NULL OR r.keyword_id = :keyword_id)  -- チップで絞り込み
ORDER BY r.talked_at DESC
LIMIT 5;
```

### キーワードのサジェスト（S-08）
```sql
SELECT k.name, COUNT(*) AS cnt
FROM records r
JOIN keywords k ON k.id = r.keyword_id
JOIN people   p ON p.id = r.person_id
WHERE p.user_id = :uid AND k.name ILIKE :q || '%'
GROUP BY k.name
ORDER BY cnt DESC LIMIT 5;
```
**全顧客を横断する。** 同じ担当者の語彙は偏るため、その方が入力が速い（4.2）。

### 話題チップ（S-08／よく使う順）
```sql
-- そのお客さんと話したことのある話題を、使用回数の多い順に
SELECT tm.id, tm.name, COUNT(r.id) AS cnt
FROM topics t
JOIN topic_masters tm ON tm.id = t.topic_master_id
LEFT JOIN records r   ON r.topic_id = t.id
WHERE t.person_id = :pid
GROUP BY tm.id, tm.name
ORDER BY cnt DESC LIMIT 5;
```

### 避ける話題（S-04〜S-07で常時表示）
```sql
SELECT tm.name
FROM topics t
JOIN topic_masters tm ON tm.id = t.topic_master_id
WHERE t.person_id = :pid AND t.is_ng = true;
```

### 今日の記録（F-10）
```sql
-- visits テーブルは持たない。records から引く（判断16）
SELECT DISTINCT p.id, p.name, p.name_kana, p.appearance
FROM records r
JOIN people p ON p.id = r.person_id
WHERE p.user_id = :uid AND r.talked_at = :today
ORDER BY p.name_kana;
```

### まだ話していない話題（F-11）
```sql
SELECT tm.name FROM topic_masters tm
WHERE (tm.user_id = :uid OR tm.user_id IS NULL)
  AND NOT EXISTS (
    SELECT 1 FROM topics t
    WHERE t.topic_master_id = tm.id AND t.person_id = :pid
  )
ORDER BY tm.sort_order LIMIT 3;
```

### スコアの再計算（保存時）
```sql
-- ① キーワード単位の EMA は、アプリ側で直近値と今回値から算出
-- ② 時間減衰をかけた値の最高と平均から、話題スコアを更新
UPDATE topics SET
  score = :new_score,
  last_talked_at = :talked_at
WHERE id = :tid;
```
計算式は 7.5 を参照。**生スコアが records に残るため、後から全件再計算できる。**

# 8. セキュリティ・個人情報

## 8.1 立ち位置

- 顧客情報を記録すること自体は、**美容室のカルテと同じで業務上当然の行為**
- SNSとは構造が違う。SNSは「本人が公開し、拡散し、二次利用される」。本アプリは「**本人だけが見て、拡散せず、二次利用しない**」
- 「SNSも同じだから仕方ない」ではなく、**「SNSより閉じた設計にした」**と主張する

## 8.2 対策

### 対策1：RLS（Row Level Security）でユーザーごとに分離

```sql
ALTER TABLE people ENABLE ROW LEVEL SECURITY;

CREATE POLICY "own rows only" ON people
  FOR ALL
  USING (user_id = auth.uid())
  WITH CHECK (user_id = auth.uid());
```

子テーブル（records / topics）は、親（people）を辿って判定する。

```sql
CREATE POLICY "own rows only" ON records
  FOR ALL
  USING (EXISTS (
    SELECT 1 FROM people p
    WHERE p.id = records.person_id AND p.user_id = auth.uid()
  ));
```

**他ユーザーのデータには構造的にアクセスできない。**

### 対策2：扱う情報を限定する

**アレルギー・既往歴などの要配慮個人情報は、そもそも対象外。**
記録するのは「会話のきっかけになる情報」だけ。人物評価ではなく事実の記録にとどめる。

## 8.3 聞かれたときの答え方

> RLSでユーザーごとにデータを分離しています。他ユーザーのデータには構造的にアクセスできません。
> また、**アレルギーなど施術・健康に関わる情報は、そもそも扱いません。** 記録するのは会話のきっかけになる情報だけです。

**2文で足りる。** 暗号化や法律の条文は、聞かれるまで言わない。

## 9.2 なぜこの構成か

**Supabaseを選ぶ理由**
認証・DB・権限管理が1つで揃う。10日で認証を自作する余裕はない。
そしてRLSがあることで、**セキュリティの説明が「構造的に不可能」で済む**（8.3）。

**PWAを選ぶ理由**
ストア審査が不要で、URLを配れば使ってもらえる。10日後にすぐ人に渡せる。

**PWAの制約（判断12・11章）**
- 写真をユーザーのiCloudに保存する経路がない（Web APIが存在しない）
- 端末内保存（IndexedDB）は機種変更で消え、iOSが削除する可能性もある
- → **写真を扱わない**という判断の技術的根拠になっている

将来ネイティブ化する場合は Capacitor でのラップを検討する。

**d3 を「座標計算だけ」に使う理由**
d3のDOM操作とReactの再描画がぶつかる。
`forceSimulation` の `onTick` で座標を state に入れ、**描画はReactのSVGで行う**（9.4）。

## 9.4 バブルチャート実装メモ

```js
d3.forceSimulation(data)
  .force('collide', d3.forceCollide(d => d.r + 2))  // 円同士がぶつかる
  .force('x', d3.forceX(W/2).strength(.045))        // 中央に引き寄せる
  .force('y', d3.forceY(H/2).strength(.055))
```

`forceCollide`（重ならない）と `forceX/Y`（中央に集まる）がせめぎ合うことで、
**ぎゅうぎゅうに詰まった状態**になる。

**常に10個固定なので、レイアウトが安定する**（点線の混在をやめたため）。

### 半径は必ず平方根スケールを使う
```js
const r = d3.scaleSqrt()
  .domain([0, d3.max(data, d => d.score)])
  .range([24, maxRadius]);   // 最小24px：指で押せる下限
```
半径を点数に比例させると**面積が二乗で増える**ため、100点が10点の100倍に見えてしまう。

### 色の決め方
```
塗り   前回話した話題 → グレー
       それ以外       → 緑。スコアが高いほど濃く
```
**大きさと色で別の情報を持たせない。** どちらもスコアを表す（濃淡は補助）。

### 実装の進め方
座標計算だけd3にやらせて、**描画はReactで行う**。
`onTick` で座標をstateに入れて再描画する。

**3日目あたりに1時間だけ試作しておく。**
動かないと分かった時点で、代替案（大小のカードを並べる）に切り替えられる。

## 11.1 「効果が出るまで2ヶ月」への対策【v5で整理】

### まず、谷があるのはバブルだけ

| 機能 | 効き始め | 優先度 |
|---|---|---|
| 避ける話題 | **初日** | 高 |
| お客さん情報（二度聞き防止） | **初日**（初期登録した分） | **最高** |
| 話題バブル | 2ヶ月後（実際の記録が要るため） | 中 |

**最重要機能である「二度聞きを防ぐ」に、谷はない。**
初回に覚えていることを書いておけば、次に会った日から役に立つ。

谷があるのはバブル（どの話題を振るか）だけで、これは情報タブより優先度が低い。
**「アプリ全体が2ヶ月使えない」わけではない。**

### 対策1：初回に、思い出せる人を登録してもらう

2段階に分ける。

```
ステップ1  名前だけ、思い出せるだけ登録する（1人3秒）
           → リストが目に見えて増える。手応えが先に来る
ステップ2  そのうち書ける人に、覚えていることを足す
           → 書かなくても進める。強制しない
```

**名前だけでも意味がある。**
翌日以降その人が来たとき、新規登録の手間なくいきなり記録できる。
日々の記録が軽くなる。

**盛り上がりの入力は、通常の記録画面と同じスライダーを使う。**
過去の記憶は曖昧だが、**曖昧なまま置いていい**のがスライダーの良さ（5章参照）。
初回専用の入力方式は作らない。実装がゼロで済む。

※初回登録の順番は指示しない。「思い出せる人＝よく来る人」である可能性が高く、
　並べ替えの判断をさせるのは判断10に反する。

### 対策2：完成形を先に見せる（サンプルデータ）

初回起動時、**2年使った状態のサンプル顧客**を1人入れておく。
バブルが育ち、キーワードが並び、会話ログが溜まった状態。

**「2ヶ月後にこうなります」を、言葉ではなく画面で見せる。**
待つ理由が具体的になる。

- ユーザーは**いつでも削除できる**
- 実装コストは、ダミーデータを1件用意するだけ

### 対策3：期待値の言い方を変える

```
× 効果が出るのは2ヶ月後です
○ 次にその人と会ったとき、役に立ちます
```

「2ヶ月」は待つ期間の長さを言っているが、「次に会ったとき」は出来事を指している。
同じことなのに、後者は具体的で近く感じる。

**そして実際、次に会うのがいつかは人による。** 2週間で来る人もいる。
「2ヶ月」と言い切ると、早く来る人がいることを隠してしまうため、正確さの点でも劣る。

### 検討したが採用しなかった案

| 案 | 却下理由 |
|---|---|
| 気分スタンプで毎日開かせる | **会わない日は開かなくていいアプリ。** 毎日開く仕組みを入れると、開けなかった日が失敗として可視化され、途切れた時点で離脱する |
| 記録が0の日も記録させる | 同上。連続日数を意識させると、途切れたときのダメージが生まれる |
| 次回予約が近い人から登録 | **予約情報を持っていない。** 次回予約を取らない客も多く、そもそも情報が存在しない |
| 書く楽しさで引っ張る | 写真・日記・コレクション性が必要になり、判断12と衝突する。競合が押さえている領域でもある |

**残った対策はすべて心理面のもので、谷そのものは短くできない。**
ここは弱点として認め、プレゼンでも自分から言う。

そのうえで、**どのアプリも「思い出す」で止まっており、「どれを話すか」には踏み込んでいない。**

## 12.2 直接競合3アプリ（2026年8月時点）

| | 人記録<br>(Yuto Inagaki) | ヒトメモ<br>(Rikuto Sato) | メモリオ<br>(Tomohiro Suzuki) |
|---|---|---|---|
| 評価 | 4.5 / 87件 | 4.3 / 360件 | **4.6 / 794件** |
| カテゴリ | ユーティリティ | ライフスタイル | ユーティリティ |
| サイズ | 21MB | 61MB | 101MB |
| 主な訴求 | 無制限登録・カスタム項目 | 名前を覚える・誕生日通知 | 写真日記・思い出・推し活 |
| 想定用途 | 婚活／就活／ビジネス／キャラ設計 | 同僚／推し活／家族の記念日 | 家族／顧客／推し活／旅行 |
| 会話の記録 | 出来事メモ（自由記述） | 自由メモ | メモ＋写真 |
| **盛り上がりの数値化** | **なし** | **なし** | **なし** |
| **可視化** | **なし** | **なし** | **なし** |
| **NG話題の警告** | **なし** | **なし** | **なし** |

### 各アプリの特徴

**人記録（Yuto Inagaki）**
「無制限」と「カスタム項目」が売り。項目を自由に追加でき、画像AIでプロフィールを
自動入力する機能まである。Excel出力、パスコード、検索条件保存など機能は豊富。
ストア画像5枚すべてが機能の多さを訴求している。
**プロフィール帳としての完成度は高い。**

**ヒトメモ（Rikuto Sato）**
「名前を忘れたことはありませんか」から始まる、**名前と顔の一致**が主眼のアプリ。
誕生日リマインダーが目玉機能。ストア画像にキャラクターのイラストが並んでおり、
推し活・二次元の記録での利用が多いと推測される。**ビジネス用途からは遠い。**

**メモリオ（Tomohiro Suzuki）— 最大の競合**
794件・4.6は3アプリで最高。**ビジネス用途で実際に使われている。**
レビューにタトゥー施術者の顧客管理、開業したサロンの顧客台帳としての利用がある。
ただし本体は**写真日記アプリ**。ストア画像5枚すべてが写真で、
旅行の思い出・推し活・お祝いイベント。
「メモを書くと日付がアイコンや写真で埋まり、日記のように楽しめます」と謳っている。

## 12.3 3アプリに共通する構造

```
人記録    属性を埋める     ┐
ヒトメモ  名前と誕生日を覚える ├→ すべて「思い出す」で完結
メモリオ  写真で思い出を残す  ┘
```

**共通点**
- 記録はすべて自由記述（テキスト＋写真）
- 用途を絞っていない（婚活・就活・推し活・顧客管理を全部カバー）
- 写真が中核（サイズ61〜101MBがそれを示す）
- **どの話題が効くかは分からない。読んで自分で判断するしかない**

**実際のレビューに現れた自由記述の限界**
「特徴とメモがゴチャゴチャになるので項目が別れているとわかりやすい」
「スクロールしなければ読めない」
→ **判断1（テキストではなく構造化データで持つ）が、実際のユーザー不満として裏付けられた。**

## 12.4 本アプリの立ち位置

```
                 思い出を残す          次の会話に使う
  プライベート   人記録／ヒトメモ／メモリオ      ―
  ビジネス       （メモリオが一部進出）    ★おぼえがき
```

**軸1：思い出を残す ／ 次に活かす**
**軸2：プライベート ／ ビジネス**

### 勝てる理由

**① 用途を1つに決めている**
競合は婚活も就活も推し活も漫画のキャラ設定も全部カバーする。
本アプリは**繰り返し会う仕事相手だけ**。
だから時間減衰も「まだ話していない」も意味を持つ。1回きりの出会いには要らない機能。

**「シンプル」ではなく「絞っている」。** メモリオも「シンプルで多機能」と謳っているので、
シンプルさの対決では差が伝わらない。**用途を1つに決めたから項目が少ない**、が正確。

**② 埋めさせない**
競合はカスタム項目を追加し放題。埋める欄が増えるほど、埋まっていないと気になる。
本アプリは4項目、しかも書かなくていい日がある（判断5）。

**③ 判断まで持っていく**
競合は情報を出すところまで。読んで判断するのは人間。
本アプリは**バブルを見れば判断が終わる**。

## 12.5 その他の周辺領域

| カテゴリ | 例 | なぜ競合しないか |
|---|---|---|
| サロン向け顧客管理システム | LiME／BeautyMerit／サロンアンサー など26種以上 | 店舗導入・施術履歴とPOSが中心。**「予約や会計の機能が多くて邪魔」というレビューが実在する** |
| 営業SFA / CRM | Salesforce／kintone | 商談・進捗・金額が対象。雑談は備考に埋もれる。会社が導入し上司が見る |
| 話題提供アプリ | ToPick など | ランダムに話題を出すだけ。相手ごとの記憶を持たない |
| 汎用メモアプリ | 標準メモ／Notion | 検索も可視化もできない |

## 12.6 正直なリスク

**スコアもバブルも、競合が後から実装できる。**
技術的に難しくない。各社の開発者は活発に更新しているので、良い機能なら取り込まれる。

守れるとすれば機能ではなく、**「会う直前に開く」という習慣**の方。
ただしこれも確実ではない。

**また、メモリオのAI似顔絵生成**（写真なしで髪型・メガネ・年齢層を選ぶとアイコンを生成）は、
本アプリの「見た目の特徴（1行）」と同じ課題を、より視覚的に解いている。**ここは向こうが上。**
