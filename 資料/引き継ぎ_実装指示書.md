## 1. プロダクト概要

**おぼえがき** — 接客業・営業職向けの会話記録アプリ。

- **コンセプト**：覚えている義理のない、何気ない話を覚えている。「そんなことまで覚えててくれたんだ」が生まれる状態をつくる
- **立ち位置**：記録アプリではなく **判断アプリ**。既存の人メモアプリは「読んで自分で判断する」で止まる
- **提供対象**：店舗ではなく、そこで働く**個人**。受益者と入力者が同一なので動機が続く
- **利用シーン**：会う直前の30秒（思い出す）／会った後の10秒（記録する）
- **前提**：1日に会うのは4人前後、覚えておく相手は約90人、次に会うのは約2ヶ月後

### 解決する課題（優先順）

| # | 課題 | 対応する機能 | 効き始め |
|---|---|---|---|
| **1** | 「それ前にも答えましたよね」（二度聞き） | お客さん情報タブ | **初日** |
| 2 | 触れてはいけない話題を振ってしまう | NG話題の常時警告 | **初日** |
| 3 | 話題は振れるが当たるかが毎回運（空振り） | 話題バブル・話題詳細のキーワード | 2ヶ月後 |
| 4 | 前回と同じ話題を続けて振る | 泡の濃淡・最終会話日 | 2ヶ月後 |
| 5 | 会話が広がらない | まだ話していない話題 | 2ヶ月後 |

**谷があるのはバブルだけ。** 主目的の 1・2 に谷はないので、実装順もこの優先順に従う。

## 4. データモデル（v7・全6テーブル）

### 全体像

```
users ──┬─< people ──┬─< topics ──< records
        │            └─< records
        ├─< topic_masters ──< topics
        └─< keywords ──o< records （nullable）
```

**バブル1個 = `topics` の1行**（人 × 話題）。田中さんの「食べ物」と佐藤さんの「食べ物」は別行。

### DDL

```sql
create extension if not exists pg_trgm;

-- 利用者。Supabase Auth と 1:1
create table users (
  id         uuid primary key,              -- auth.users.id と同一
  email      text not null,
  created_at timestamptz not null default now()
);

-- お客さん
create table people (
  id             uuid primary key default gen_random_uuid(),
  user_id        uuid not null references users(id) on delete cascade,
  name           text not null,             -- 唯一の必須項目
  name_kana      text,
  age_group      text,
  gender         text,
  appearance     text,                      -- 「、」区切りで複数可
  company        text,                      -- 検索対象・サジェスト対象
  position       text,                      -- 表示のみ。検索対象に含めない
  group_id       int default 1,             -- v6で廃止。カラムのみ残す
  last_talked_at date,                      -- 一覧の並び順（意図的な冗長カラム）
  created_at     timestamptz not null default now()
);
create index idx_people_user on people(user_id);
create index idx_people_last on people(user_id, last_talked_at desc);
create index idx_people_search on people using gin (
  (name || ' ' || coalesce(name_kana,'') || ' '
   || coalesce(appearance,'') || ' ' || coalesce(company,'')) gin_trgm_ops);

-- 話題マスタ。user_id が NULL なら初期マスタ（全員に見える）
create table topic_masters (
  id         uuid primary key default gen_random_uuid(),
  user_id    uuid references users(id) on delete cascade,   -- NULL可
  name       text not null,
  sort_order int not null default 0,
  created_at timestamptz not null default now()
);
create unique index idx_topic_master_uniq
  on topic_masters(coalesce(user_id::text,'global'), name);

-- 人 × 話題（バブル1個）
create table topics (
  id              uuid primary key default gen_random_uuid(),
  person_id       uuid not null references people(id) on delete cascade,
  topic_master_id uuid not null references topic_masters(id) on delete restrict,
  score           numeric(5,2) not null default 0,   -- バブルの大きさ（キャッシュ）
  is_ng           boolean not null default false,
  last_talked_at  date,
  created_at      timestamptz not null default now()
);
create unique index idx_topics_uniq on topics(person_id, topic_master_id);
create index idx_topics_bubble on topics(person_id, is_ng, score desc);

-- キーワードマスタ。利用者単位（全顧客を横断してサジェスト）
create table keywords (
  id         uuid primary key default gen_random_uuid(),
  user_id    uuid not null references users(id) on delete cascade,
  name       text not null,
  created_at timestamptz not null default now()
);
create unique index idx_keywords_uniq on keywords(user_id, name);
create index idx_keywords_suggest on keywords(user_id, name text_pattern_ops);

-- ★本体。1回の保存＝1レコード
create table records (
  id         uuid primary key default gen_random_uuid(),
  person_id  uuid not null references people(id)   on delete cascade,
  topic_id   uuid not null references topics(id)   on delete cascade,
  keyword_id uuid          references keywords(id) on delete set null,
  score      smallint not null check (score between 0 and 100),
  content    text,                              -- nullable。空でも保存できる
  talked_at  date not null,                     -- 深夜は前日扱い（午前4時まで）
  created_at timestamptz not null default now()
);
create index idx_records_person   on records(person_id, talked_at desc);
create index idx_records_topic    on records(topic_id, talked_at desc);
create index idx_records_keyword  on records(keyword_id, talked_at desc);
create index idx_records_content  on records(person_id, talked_at desc)
  where content is not null;
```

### 外部キーと ON DELETE（全8本・v7で確定）

| 子 | カラム | 参照先 | ON DELETE | 理由 |
|---|---|---|---|---|
| people | user_id | users | **CASCADE** | アカウント削除で全データを落とす |
| topic_masters | user_id | users | **CASCADE** | 同上 |
| keywords | user_id | users | **CASCADE** | 同上 |
| topics | person_id | people | **CASCADE** | お客さんを消せば話題も消える |
| topics | topic_master_id | topic_masters | **RESTRICT** | 使用中の話題名は消させない |
| records | person_id | people | **CASCADE** | |
| records | topic_id | topics | **CASCADE** | |
| records | keyword_id | keywords | **SET NULL** | **記録は残す** |

- **`keyword_id` だけ SET NULL**：CASCADE だとキーワードを消しただけで会話の記録が消える。キーワードは分類のための語であって記録の本体ではない
- **`topic_master_id` を RESTRICT**：話題名を消すと topics → records が連鎖で消え、「食べ物」を消しただけで食べ物の会話が全部消える事故になる
- アカウント削除は `auth.users` を消せば `public.users` も CASCADE で落ちる。アプリ側で順に DELETE する必要はない

### RLS

```sql
-- people / keywords：user_id で直接判定
alter table people enable row level security;
create policy "own rows only" on people for all
  using (user_id = auth.uid()) with check (user_id = auth.uid());

-- records / topics：親を辿って判定
alter table records enable row level security;
create policy "own rows only" on records for all
  using (exists (select 1 from people p
                 where p.id = records.person_id and p.user_id = auth.uid()));

-- topic_masters：初期マスタ（user_id IS NULL）は全員に見せる
alter table topic_masters enable row level security;
create policy "own or global" on topic_masters for select
  using (user_id = auth.uid() or user_id is null);
create policy "own rows only" on topic_masters for insert
  with check (user_id = auth.uid());
```

- **「その他」を入れない。** あると全部そこに逃げる
- `sort_order` が効くのは**新規のお客さんの記録画面だけ**。2回目以降は実績順に置き換わる（§6）

### 設計判断（変えてはいけない理由）

- **`records.content` が nullable であることが設計の要**。同じ話で盛り上がっただけの日は話題とスコアだけで保存できる。これが「10秒で終わる」を成立させている
- **`score` と `talked_at` を全件保存することが、唯一の「取り返しがつかない」設計判断**。これがあれば計算式は後から変更できる
- **`is_ng` を score と分ける**。「反応が薄い（20点）」と「触れてはいけない」は意味が違う。**NG の理由は保存しない**（要配慮個人情報になり得る）
- **`people` に score を持たない**。点数が付くのは話題であって人ではない。「田中さん 80点」に見える画面は第三者に見られた時点で終わる
- **写真のカラムを持たない**。PWA には iCloud への保存経路がなく、IndexedDB は機種変更で消える
- **`position` は検索対象に含めない**
- **導出できるものは持たない。ただし読み取り頻度が高いものは意図的な非正規化として持つ**（`people.last_talked_at` と `topics.score` だけが例外）
- 扱わない情報：アレルギー・既往歴などの要配慮個人情報、写真、日記、NG理由

## 5. 盛り上がりスコア（3段構え）

> **正は `資料/スコアの仕組み.py`。** `python3 資料/スコアの仕組み.py` で挙動を確認できる。

### ① キーワードスコア（指数移動平均）

```
新score = 旧score × (1 − c) + 今回score × c    ／ 初回は今回値をそのまま
```

| 前回からの経過日数 | c |
|---|---|
| 7日以内 | 0.20 |
| 8〜30日 | 0.35 |
| 31日以上 | 0.50 |

間隔が空くほど新しい値を重く見ることで、来店ペースの違う業種に同じ式で対応できる。

### ② 表示値（時間減衰）

```
表示値 = キーワードスコア × 減衰率
```

| 最終会話からの日数 | 減衰率 |
|---|---|
| 90日以内 | 1.00 |
| 91〜180日 | 0.90 |
| 181〜365日 | 0.80 |
| 366日以上 | 0.65 |

最高値方式は「忘れない」ため、減衰がないと1年前の当たりが永久に上位を占める。**時間減衰は削らない。**

### ③ 話題スコア（階層集約）

```
話題score = 配下キーワードの表示値の最高 × 0.7 + 平均 × 0.3
```

滑ったのは振り方であって話題ではない。最高値で当たりを拾い、平均でノイズに強くする。

| ケース | 最高 | 平均 | 話題score |
|---|---|---|---|
| 大谷90・イチロー40 | 90 | 65 | **83** |
| 大谷90のみ | 90 | 90 | **90** |
| 全部50 | 50 | 50 | **50** |

### TypeScript 移植（`lib/score.ts`）

```ts
const coef = (gapDays: number | null) =>
  gapDays === null ? 1.0 : gapDays <= 7 ? 0.2 : gapDays <= 30 ? 0.35 : 0.5;

const decay = (days: number) =>
  days <= 90 ? 1.0 : days <= 180 ? 0.9 : days <= 365 ? 0.8 : 0.65;

const days = (from: Date, to: Date) => Math.round((+to - +from) / 86_400_000);

type Rec = { keywordId: string | null; score: number; talkedAt: Date };

export const NONE = "__none__";   // キーワードなしの記録をまとめる疑似枠

/** キーワード単位の EMA。keyword_id が NULL の記録群は NONE の1枠にまとめる */
export function keywordEmas(records: Rec[]): Map<string, { ema: number; last: Date }> {
  const byKeyword = new Map<string, { ema: number; last: Date }>();
  for (const r of [...records].sort((a, b) => +a.talkedAt - +b.talkedAt)) {
    const key = r.keywordId ?? NONE;
    const prev = byKeyword.get(key);
    const c = coef(prev ? days(prev.last, r.talkedAt) : null);
    byKeyword.set(key, {
      ema: prev ? prev.ema * (1 - c) + r.score * c : r.score,
      last: r.talkedAt,
    });
  }
  return byKeyword;
}

/** ある話題の records 全件から、今日時点の話題スコアを求める */
export function topicScore(records: Rec[], today: Date): number | null {
  // 減衰は「キーワードごと」に、そのキーワードの最終会話日からかける。
  // 話題に対して一律1回ではない（そうすると古い当たりが減衰しない）
  const vals = [...keywordEmas(records).values()]
    .map(v => v.ema * decay(days(v.last, today)));
  if (vals.length === 0) return null;
  const max = Math.max(...vals);
  const avg = vals.reduce((a, b) => a + b, 0) / vals.length;
  return max * 0.7 + avg * 0.3;
}

/** topics.score に保存する値（減衰前の集約値） */
export function topicScoreUndecayed(records: Rec[]): number | null {
  const vals = [...keywordEmas(records).values()].map(v => v.ema);
  if (vals.length === 0) return null;
  const max = Math.max(...vals);
  const avg = vals.reduce((a, b) => a + b, 0) / vals.length;
  return max * 0.7 + avg * 0.3;
}
```

**`lib/score.ts` を独立させる。** 計算方式を変えるとき触るのはこの1ファイルだけ。

### 計算の全体像（2026-08-19 確定）

```
records（生データ・唯一の正）
  ↓ キーワード単位で EMA（keyword_id IS NULL の記録群も __none__ という1枠として扱う）
キーワードスコア（DBに保存しない）
  ↓ キーワードごとに、そのキーワードの最終会話日から時間減衰をかける
表示値
  ↓ 最高 × 0.7 + 平均 × 0.3
話題スコア
```

**キーワード単位の EMA を持つカラムはどこにもない**（`keywords` は名前だけのマスタ）。**`records` から都度計算する。**

#### `keyword_id IS NULL` の扱い【確定】

**入れる。** 疑似枠 `__none__` として、他のキーワードと完全に同列に扱う。

- NULL の記録群を1つのキーワードとみなして EMA を回す
- 時間減衰も他と同じようにかける（特別扱いしない）
- 階層集約（最高×0.7＋平均×0.3）の対象にも含める
- **ただし話題詳細のチップには表示しない**（名前がないため）

判断5で「前回と同じ話をした日は、話題と盛り上がりだけで10秒保存できる」と決めている以上、この記録がバブルに反映されないなら保存する意味がない。

#### キーワードスコアは EMA【確定】

§7.5① の EMA が正。**設計書 §7.6「話題詳細のキーワード」のクエリが `AVG(r.score)` になっているのは誤り。**
AVG を使うと階層集約の入力が変わり、話題スコアの計算結果まで変わってしまう。

**EMA は SQL で書きにくいため、クエリは生データを取得するだけにして、計算は `lib/score.ts` で行う。**

```sql
-- クエリは生データのみ
SELECT keyword_id, score, talked_at
FROM records
WHERE person_id = :pid AND topic_id = :tid
ORDER BY talked_at ASC;
```

#### 時間減衰は表示時に計算する【確定】

**DBに減衰後の値を保存しない。** 保存時に焼き込むと、3ヶ月後に開いても減衰していない値が出てしまう。

**減衰はキーワードごとにかける**（そのキーワードの最終会話日からの経過日数で算出）。話題に対して一律に1回かけるのではない。

> ⚠️ **この点は要注意。** 話題単位で `topics.last_talked_at` から1回だけ減衰をかける実装にすると、**一部のキーワードだけ放置されている話題で古い当たりが減衰しなくなる。**
> 検証ケース【4】（大谷90を最初に振り、以後イチロー・甲子園だけを振り続ける）の420日時点で、
> **キーワードごと＝54.4（「忘れる ✓」）／話題に1回＝約80（忘れない）** と結果が割れる。
> 後者では `topics.last_talked_at` が直近のイチローの日付になるため減衰率が1.00になり、大谷の90が永久に残る。
> §10.4「時間減衰は削らない。最高値を採る方式では減衰がないと古い当たりを永久に忘れない」が成立しなくなるため、**必ずキーワード単位でかける。**

#### `topics.score` の位置づけ

キーワード単位の減衰を表示時にかける以上、**表示のたびに `records` から計算する**ことになる。
1人分の records（2年で100〜200行程度）なので実測上は軽い。判断16 が懸念する「全レコードの集計」は全顧客横断の話であり、ここには当たらない。

| | 用途 |
|---|---|
| **`records`** | **唯一の正。** 表示値はここから計算する |
| `topics.score` | 保存時に更新するキャッシュ。一次絞り込みの `ORDER BY score DESC` に使う |

`topics.score` には**減衰前の集約値**（減衰をかけずに EMA を集約した値）を入れる。減衰済みの値を入れると時間とともに嘘になる。

#### 一次絞り込みで `LIMIT 10` にしないこと

`topics.score` は減衰前の値なので、**減衰後の順位と入れ替わりうる。**

```
score順10位のA（減衰前80）→ 古くて減衰 → 表示値 52
score順11位のB（減衰前78）→ 減衰なし   → 表示値 78   ← Aを追い抜く
```

`LIMIT 10` で切ると B を取りこぼす。**多めに取って、減衰後に再ソートしてから上位10件を確定させる。**

```
① topics を score DESC で多めに取得（is_ng = false）
② 各話題の records から表示値を計算（キーワード単位のEMA → 減衰 → 階層集約）
③ 表示値で再ソートし、上位10件をバブルに描く
```

**実装上は全件取ってよい。** バブル画面は下の「盛り上がった順　全10件」リストのために結局全件必要（§7.6 も「`LIMIT` を外して全件取得」）であり、1人あたりの話題数は大枠10〜12個程度なので、全件計算しても負荷は変わらない。**全件取れば取りこぼしがゼロになり、閾値の調整も要らない。**

話題数が多いユーザーへの上限を設ける場合は `LIMIT 15` 程度を目安にする。

### 採用しなかった案

| 案 | 却下理由 |
|---|---|
| 単純平均 | キーワードの当たり外れが話題の評価を潰す |
| 最新値のみ | 1回のブレで乱高下する |
| 最小値 | 平凡な話題ばかりが残る |
| **登場回数** | **汎用話題が全顧客で最大になり、全員のバブルが同じ顔になる。** 「振る→回数増→目立つ→また振る」の自己強化ループも起きる |

## 6. 1回の保存で起きること

```
[保存] を押すと
  1. 新規の話題名・キーワード名があれば、先にマスタへ INSERT（topic_masters / keywords）

  5. topics.last_talked_at を更新
  6. people.last_talked_at を更新
  7. 「この話題は避けたほうがいい」がチェックされていれば topics.is_ng = true
```

- 配置：`forceCollide(d => d.r + 2)` ＋ `forceX(W/2, .045)` / `forceY(H/2, .055)`
- **`onTick` で座標を state に入れ、描画は React の SVG で行う**（d3 の DOM 操作と React の再描画がぶつかるため、d3 は座標計算だけ）
- 下：「まだ話していない：」＋チップ3つ＋「>」
- さらに下：「盛り上がった順　全10件」リスト（話題名＋横バー＋スコア）。`LIMIT` を外して全件
- **「最有力」カードは置かない**（バブルと競合して目が散る）

### S-07 話題詳細

## 11. 設計方針（迷ったときの3基準）

**01. ノイズは仕組みで吸収し、ユーザーに判定させない**
機嫌が悪かったのか話題が滑ったのかは本人にも分からない。分からないものを入力させても入るのは推測だけ。§5 の計算式そのものがこの方針の実装。
**ただし NG話題は例外。** 「触れてはいけない」はサンプルが増えても薄まらず、1回の失敗が取り返しつかない。

**02. 点数を付けるのは話題であって、人ではない**
人単位の総合スコアは持たない。一覧に数値は一切出さない。数字が出るのは詳細を開いて話題タブに入ってから。
**第三者に画面を見られても、数字が話題に付いていることが分かる配置にする。**

**03. 扱わない情報を、先に決めておく**
アレルギー・既往歴は対象外。写真も日記も持たない。記録するのは会話のきっかけになる情報だけ。RLS で他ユーザーのデータには構造的に触れない。

### セキュリティを聞かれたときの答え方

> RLS でユーザーごとにデータを分離しています。他ユーザーのデータには構造的にアクセスできません。
> また、アレルギーなど施術・健康に関わる情報は、そもそも扱いません。記録するのは会話のきっかけになる情報だけです。

**2文で足りる。** 暗号化や法律の条文は、聞かれるまで言わない。

#### `text/*` は `ink/*` に改名して取り込む【決定】

Figma の色名 `text-primary` をそのまま `--color-text-primary` にすると、
Tailwind が生成するクラスは `text-text-primary` になり、
**一番書きたくなる `text-primary` が「存在しないクラス」になって無言で無視される**（実測確認済み）。

そこで **Tailwind 側だけ `ink` に改名する。** 変換規則は機械的に1つだけ。

```
Figma:  text/X   →   Tailwind:  ink-X
```

| Figma バリアブル | Tailwind トークン | クラス | hex |
|---|---|---|---|
| `text-primary` | `--color-ink-primary` | `text-ink-primary` | `#2C2C2C` |
| `text-secondary` | `--color-ink-secondary` | `text-ink-secondary` | `#8B918D` |
| `text-tertiary` | `--color-ink-tertiary` | `text-ink-tertiary` | `#78807C` |
| `text-muted` | `--color-ink-muted` | `text-ink-muted` | `#A0A5A2` |
| `text-placeholder` | `--color-ink-placeholder` | `text-ink-placeholder` | `#B6BAB7` |

**この5つ以外は Figma 名をそのまま使う。** 改名するのは `text/*` グループだけ。

> Figma 側を触る必要はない。バリアブルを更新したときは、この5つだけ読み替えて取り込む。

#### Space コレクションは取り込まない

Figma の Space（4 / 8 / 12 / 16 / 24）は **Tailwind 4 の既定スケールと一致している**ので、
トークンを定義する必要がない。既定は `--spacing: 4px` で、`p-1`=4px … `p-4`=16px。

| Figma | Tailwind |
|---|---|
| 4px | `p-1` `gap-1` |
| 8px | `p-2` `gap-2` |
| 12px | `p-3` `gap-3` |
| 16px | `p-4` `gap-4` |
| 24px | `p-6` `gap-6` |

> ⚠️ **書き出された `spacing: { "4": "4px" }` をそのまま入れないこと。**
> `p-4` が 16px から 4px に変わり、Tailwind の標準と食い違う。

なお Radius コレクションも `spacing` キーで書き出されているが、これはプラグイン側の誤り。
`--radius-*` として取り込む（値 5 / 12 / 14 / 16 / 999 は仕様と一致）。

#### タイプスケールの使い方

`text-title` の1クラスで**サイズ・行間・ウェイト・字間が同時に決まる**。

```tsx
<h1 className="text-title">田中 みか</h1>       {/* 28px / 1.2 / W700 / .02em */}
<p  className="text-body text-ink-primary">…</p>  {/* 16px / 1.7 / W400 */}
<span className="text-sub text-ink-muted">前回 2026/02/03</span>
```

| トークン | 仕様 | 用途 |
|---|---|---|
| `text-score` | 32 / W700 | スコア |
| `text-title` | 28 / W700 | 画面タイトル |
| `text-heading` | 22 / W700 | 見出し |
| `text-header` | 18 / W700 | ヘッダー |
| `text-name` | 17 / W500 | 名前・入力 |
| `text-body` | 16 / W400 | 本文 |
| `text-action` | 15 / W400 | リンク・戻る・もっと見る |
| `text-label` | 14 / W500 | ラベル |
| `text-sub` | 13 / W400 | 補助（前回日付など） |
| `text-caption` | 11.5 / W400 | キャプション |

**`text-[28px]` のような直書きをしない。** 仕様外のサイズが混ざらなくなる。

> ⚠️ **`text-link` は使えない。**
> Figma に色バリアブル `link`（= accent-500）があり、`--color-link` と `--text-link` が
> 同じ `text-link` クラスを取り合って**色が勝ち、サイズ指定が無視される**（実測確認済み）。
> 15px のリンク文字は **`text-action`** を使う。色は `text-link` で当てる。
>
> ```tsx
> <a className="text-action text-link">お客さん一覧</a>
> ```
> サイズが `text-action`、色が `text-link`。役割が分かれている。

**行間の割り振り**：仕様に明記があるのは「本文1.7／見出し1.2」の2つだけ。
残りは **見出し系（score / title / heading / header）を1.2、body を1.7、それ以外を1.5** とした。
`name` は入力欄にも使うため、1.2 では窮屈・1.7 では間延びするので1.5。

**字間**：仕様の「タイトル .02em」を `text-title` にのみ適用した。
「英字キャプション .05〜.08em」は英字のときだけなので、トークンには入れず
必要な箇所で `tracking-[0.06em]` を足す。

**`font-feature-settings: "palt"` は入れない。** 仕様が字間を数値で指定しているため、
併用すると想定より詰まる。

**フォールバック**：仕様は `Hiragino Sans, system-ui`。
Windows で確認・発表する可能性を考えて `Noto Sans JP` / `Yu Gothic` / `Meiryo` を足してある
（iOS・macOS では Hiragino が先に当たるので影響なし）。不要なら削ってよい。

`--color-*` → `bg-*` / `text-*` / `border-*`、`--radius-*` → `rounded-*`、`--font-*` → `font-*` が自動で生えます。

### 12-5. `app/layout.tsx`（フォント）

```tsx
import type { Metadata } from "next";
import { Zen_Kaku_Gothic_New } from "next/font/google";
import "./globals.css";

const zen = Zen_Kaku_Gothic_New({
  weight: ["400", "500", "700"],
  display: "swap",
  preload: false,        // 必須。付けないと preload が239個出る（下記）
  variable: "--font-zen-kaku",
});

export const metadata: Metadata = {
  title: "おぼえがき",
  description: "会う直前の30秒で、前回の話を思い出す。",
};

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="ja">
      <body className={`${zen.variable} font-zen bg-neutral-bg text-ink-primary antialiased`}>
        {children}
      </body>
    </html>
  );
}
```

#### `preload: false` が要る理由（実測比較）

同じページを4通りの設定でビルドして比較した結果。

| 設定 | ビルド | 日本語表示 | `<link rel=preload>` |
|---|---|---|---|
| `subsets: ["japanese"]` | **エラー** | — | — |
| `subsets` も `preload` も書かない | **エラー** | — | — |
| `subsets: ["latin"]` のみ | 成功 | **出る** | **239個** ← 重い |
| **`preload: false`（`subsets` なし）** | 成功 | **出る** | **0個** ← 採用 |
| `subsets: ["latin"], preload: false` | 成功 | 出る | 0個 |

**ビルドが通った3通りは、生成物が完全に同一だった。**
`@font-face` 364個（うち日本語レンジ84）／woff2 363ファイル／4.8MB。

> つまり **`subsets` の指定有無で、日本語が出るかどうかは変わらない。**
> Zen Kaku Gothic New の日本語グリフは `subsets` の対象外の範囲として常に含まれる。

**効くのは `preload: false` だけ。** これを付けないと 239個の `<link rel="preload">` が出力され、
ページを開いた瞬間に使いもしないフォントを大量に先読みする。

`preload: false` にすると先読みが止まり、ブラウザは `unicode-range` を見て
**画面に実際に出ている文字の範囲だけ**を取得する。4.8MB はディスク上の総量であって、転送量ではない。

**エラー回避のためには `subsets` か `preload: false` のどちらかが必須。**
`preload: false` を選ぶので `subsets` は書かない。
